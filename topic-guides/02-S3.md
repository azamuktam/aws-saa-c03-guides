# Section 2: S3 — Simple Storage Service

## The idea

**Amazon S3 (Simple Storage Service)** is an **object storage** service.

It stores data as:

```text
Bucket
  ↓
Object
  ├── Data
  ├── Key (object name)
  └── Metadata
```

S3 is not:

* a block disk → **EBS**
* a shared filesystem → **EFS / FSx**

You normally replace an entire object rather than modifying individual bytes inside it.

### Important S3 facts

* S3 is **highly durable**: designed for **99.999999999% durability**.
* A bucket belongs to **one AWS Region**.
* Bucket names must be **globally unique**.
* A single object can be up to **5 TB**.
* S3 has **unlimited total storage**.

### S3 key

An S3 object has a **key**, which looks like a path:

```text
photos/2026/cat.jpg
```

S3 does not have traditional folders. `photos/2026/` is part of the object's key.

---

# S3 storage classes

S3 storage classes mainly differ in:

1. **How often the data is accessed**
2. **How quickly the data must be retrieved**
3. **How much storage should cost**

| Storage class                     | Access pattern                                     | Retrieval                    | Minimum storage |
| --------------------------------- | -------------------------------------------------- | ---------------------------- | --------------- |
| **S3 Standard**                   | Frequently accessed                                | Milliseconds                 | None            |
| **S3 Intelligent-Tiering**        | Unknown / changing access pattern                  | Milliseconds in active tiers | None            |
| **S3 Standard-IA**                | Infrequently accessed                              | Milliseconds                 | 30 days         |
| **S3 One Zone-IA**                | Infrequent + re-creatable                          | Milliseconds                 | 30 days         |
| **S3 Glacier Instant Retrieval**  | Rarely accessed, but must be immediately available | Milliseconds                 | 90 days         |
| **S3 Glacier Flexible Retrieval** | Archive, retrieval can take minutes to hours       | Minutes to hours             | 90 days         |
| **S3 Glacier Deep Archive**       | Very rarely accessed, long-term archive            | Hours                        | 180 days        |

S3 Glacier classes have the same high durability model as S3 Standard while offering lower storage costs.

---

# The 3-filter method

When the exam asks for the **most cost-effective storage class**, use these three filters.

## Filter 1 — How often is the data accessed?

```text
Frequently
    ↓
S3 Standard

Unknown / unpredictable
    ↓
S3 Intelligent-Tiering

Infrequently
    ↓
Standard-IA / One Zone-IA

Rarely
    ↓
Glacier classes
```

## Filter 2 — How quickly must it be retrieved?

```text
Milliseconds
    ↓
Standard
Standard-IA
One Zone-IA
Glacier Instant Retrieval

Minutes to hours
    ↓
Glacier Flexible Retrieval

Hours are acceptable
    ↓
Glacier Deep Archive
```

Glacier Flexible Retrieval is archival storage and normally requires a restore before the object can be accessed. Deep Archive is even cheaper but is designed for workloads that can wait hours for retrieval.

## Filter 3 — How long will the object remain there?

Important minimum storage durations:

```text
Standard-IA        → 30 days
One Zone-IA        → 30 days
Glacier Instant    → 90 days
Glacier Flexible   → 90 days
Glacier Deep       → 180 days
```

If you delete or transition the object before the minimum duration, you can still be charged for the remaining minimum period.

### Example

> "Data is accessed twice per year and must be retrievable within 10 minutes."

Reasoning:

```text
Rare access
→ Glacier family

10 minutes
→ Deep Archive is too slow

Need immediate access?
→ No, so Glacier Instant Retrieval is unnecessary

Best fit
→ Glacier Flexible Retrieval
```

---

# S3 Standard

Use S3 Standard when:

* Data is accessed frequently.
* Low-latency access is required.
* Access patterns are predictable.

### Exam signal

> "Frequently accessed data"

→ **S3 Standard**

---

# S3 Intelligent-Tiering

Use Intelligent-Tiering when the access pattern is **unknown or changes unpredictably**.

S3 automatically moves objects between access tiers based on access behavior.

There is a small monitoring/automation charge.

### Exam signal

> "Access patterns are unknown."

> "Data access changes unpredictably."

→ **S3 Intelligent-Tiering**

### Important distinction

If you already know exactly when the data will become less active:

```text
Known lifecycle
→ Lifecycle rule
```

If you do not know the future access pattern:

```text
Unknown access pattern
→ Intelligent-Tiering
```

S3 Intelligent-Tiering now has active tiers and optional archive tiers, so for SAA the important signal is simply **unknown/unpredictable access**.

---

# S3 Standard-IA

Use Standard-IA when:

* Data is accessed less frequently.
* Data must still be retrieved immediately.
* The data needs multi-AZ resilience.

### Exam signal

> "Infrequently accessed but must be immediately available."

→ **S3 Standard-IA**

---

# S3 One Zone-IA

One Zone-IA stores data in **one Availability Zone**.

Because it uses only one AZ, it is cheaper but less resilient than Standard-IA.

Use it when the data is:

* Infrequently accessed
* Re-creatable
* A secondary copy
* Not worth storing redundantly across multiple AZs

### Exam signal

> "Data can be regenerated."

> "Secondary copy."

> "Re-creatable."

→ **S3 One Zone-IA**

Do **not** use One Zone-IA for the only copy of irreplaceable data.

---

# S3 Glacier Instant Retrieval

Use this for data that:

* Is rarely accessed
* Must still be retrieved immediately
* Needs millisecond access

Typical access pattern:

```text
Once every few months
+
Immediate retrieval
```

### Exam signal

> "Archive data but must retrieve it immediately."

→ **Glacier Instant Retrieval**

---

# S3 Glacier Flexible Retrieval

Use this for archival data when retrieval can take **minutes to hours**.

It is cheaper than Glacier Instant Retrieval.

### Exam signal

> "Archive data."

> "Retrieval within minutes/hours is acceptable."

→ **Glacier Flexible Retrieval**

---

# S3 Glacier Deep Archive

Use this for very long-term archival data.

Typical examples:

* Regulatory records
* Compliance archives
* Data retained for many years
* Data accessed less than once a year

It is the **lowest-cost S3 storage class**, but retrieval takes hours.

### Exam signal

> "Cheapest possible archive storage."

> "Data is retained for years."

> "Retrieval within many hours is acceptable."

→ **S3 Glacier Deep Archive**

Current AWS documentation describes Deep Archive standard retrieval as typically around 12 hours, with retrieval options spanning longer periods.

---

# Lifecycle rules

Lifecycle rules automatically transition or delete objects.

Example:

```text
Day 0
S3 Standard
   ↓
Day 30
Standard-IA
   ↓
Day 90
Glacier Instant Retrieval
   ↓
Day 365
Delete
```

Lifecycle rules can:

* Transition objects to cheaper storage classes
* Expire objects
* Delete old versions
* Abort incomplete multipart uploads

### Exam signal

> "The access pattern is known and changes according to a schedule."

→ **S3 Lifecycle**

---

# Versioning

Versioning keeps multiple versions of an object.

Example:

```text
report.pdf
   ↓ overwrite
Version 1
Version 2
```

A normal delete does not immediately remove the old version.

Instead, S3 adds a **delete marker**.

```text
Version 1
Version 2
Delete marker
```

Remove the delete marker and the object becomes visible again.

### Important

Once S3 Versioning is enabled, you can:

* suspend it

but you cannot return the bucket to the original **unversioned state**.

### Exam signal

> "Protect against accidental overwrite or deletion."

→ **S3 Versioning**

---

# MFA Delete

MFA Delete adds an extra protection mechanism to S3 Versioning.

Certain operations require the root user's MFA authentication.

It is useful for protecting against:

* Accidental permanent deletion of object versions
* Malicious deletion
* Accidental suspension of versioning

### Exam signal

> "Require MFA before permanently deleting S3 object versions."

→ **MFA Delete**

---

# S3 Object Lock — WORM protection

**S3 Object Lock** provides **WORM** protection:

**Write Once, Read Many**

It prevents protected object versions from being overwritten or deleted during their protection period. Object Lock requires Versioning. AWS now also allows Object Lock to be enabled on an existing general-purpose bucket; once enabled, it cannot be disabled, and Versioning cannot be suspended for that bucket.

Architecture:

```text
S3 bucket
   ↓
Versioning
   ↓
Object Lock
   ↓
Protected object version
```

---

# Object Lock: Compliance vs Governance

This is one of the highest-value SAA S3 distinctions.

|                                            | **Governance mode** | **Compliance mode** |
| ------------------------------------------ | ------------------- | ------------------- |
| Normal users can delete?                   | No                  | No                  |
| Authorized users can bypass?               | **Yes**             | **No**              |
| Strict regulatory immutability?            | Less suitable       | **Yes**             |
| "Even administrators/root must not bypass" | No                  | **Yes**             |

### Governance mode

Governance mode protects objects from normal changes.

However, users with the appropriate **`s3:BypassGovernanceRetention`** permission can bypass the retention protection.

### Exam signal

> "Admins may be allowed to override the protection."

→ **Governance mode**

---

### Compliance mode

Compliance mode is much stricter.

During the retention period, the protected object version cannot be deleted or overwritten through normal AWS permissions, including by administrators or the root user. AWS documents the key compliance behavior explicitly.

### Exam signal

> "Not even administrators can delete it."

> "Even the root user must be restricted."

> "Regulatory compliance requires immutable records."

→ **Compliance mode**

---

# Retention period vs Legal Hold

Do not confuse these.

## Retention period

The object is protected until a **specific date**.

Example:

```text
January 1, 2026
       ↓
Protected for 1 year
       ↓
January 1, 2027
       ↓
Retention expires
```

Use this when the question gives a **fixed period**:

* 1 year
* 5 years
* 7 years

### Exam signal

> "Protect the object for exactly one year."

→ **Retention period**

---

## Legal Hold

A legal hold does **not depend on a fixed retention expiry**.

It keeps the object protected until the legal hold is explicitly removed.

Typical scenario:

```text
Lawsuit begins
      ↓
Legal Hold ON
      ↓
Keep object protected
      ↓
Case ends
      ↓
Legal Hold removed
```

### Exam signal

> "Litigation"

> "Legal investigation"

> "Keep records until the case is closed"

→ **Legal Hold**

---

# Question 47: Object Lock

The question says:

* S3
* Versioning enabled
* Cannot overwrite/delete
* Exactly **one year**
* Even **root** must not bypass
* Strict compliance

Break it down:

```text
Cannot delete/overwrite
→ Object Lock

Root must not bypass
→ Compliance mode

Exactly one year
→ Retention period

Final answer
→ Object Lock + Compliance mode + 1-year retention
```

### Answer-choice analysis

**1. Compliance mode + legal hold of one year**

Wrong.

Compliance mode is correct, but a legal hold is not the normal fixed-period mechanism. A legal hold remains until explicitly removed.

**2. Compliance mode + retention period of one year**

✅ **Correct**

```text
Object Lock
+
Compliance mode
+
1-year retention
```

**3. Governance mode + legal hold**

Wrong.

Governance mode can be bypassed by appropriately authorized users, and a legal hold is not the normal answer for a fixed one-year period.

**4. Governance mode + retention period**

Wrong.

The one-year retention period is correct, but Governance mode does not provide the required strongest immutability because authorized users can bypass governance retention.

### Memorize this:

```text
Fixed time
+
Nobody can bypass
        ↓
Compliance mode + Retention period
```

---

# Object Lock vs Versioning

They solve different problems.

### Versioning

Protects against accidental deletion/overwrite by keeping previous versions.

```text
Object
 ↓
Version 1
Version 2
Version 3
```

But users with sufficient permissions can still delete versions.

### Object Lock

Adds WORM protection to object versions.

```text
Version
 ↓
Object Lock
 ↓
Cannot delete/overwrite during retention
```

### Exam distinction

> "Recover an accidentally deleted object."

→ **Versioning**

> "Nobody should be able to delete the object for 5 years."

→ **Object Lock**

---

# Object Lock and replication

S3 Object Lock can work with S3 Replication.

When replicating locked objects:

* Source and destination buckets must have Object Lock enabled.
* S3 can replicate the retention metadata as well.

This is useful when compliance data also needs a second copy in another bucket or Region.

---

# Replication

S3 can automatically replicate objects between buckets.

## Cross-Region Replication — CRR

Copies objects to another AWS Region.

Typical uses:

* Disaster recovery
* Compliance
* Geographic separation
* Lower latency for users in another Region

```text
Region A
S3 bucket
   ↓
CRR
   ↓
Region B
S3 bucket
```

## Same-Region Replication — SRR

Copies objects to another bucket in the same Region.

Typical uses:

* Log aggregation
* Production → test
* Separate accounts/buckets
* Data isolation

### Replication requirement

For standard S3 replication:

> **Versioning must be enabled on both source and destination buckets.**

### Existing objects

Normal replication is designed around objects eligible after replication is configured.

If you need to replicate **existing objects**, use:

→ **S3 Batch Replication**

### Exam signal

> "Replication is configured, but old objects were not copied."

→ **S3 Batch Replication**

---

# Encryption

S3 encrypts new objects by default.

The main customer-visible encryption options are:

| Encryption                 | Who manages key material? | Main signal                      |
| -------------------------- | ------------------------- | -------------------------------- |
| **SSE-S3**                 | AWS                       | Simple server-side encryption    |
| **SSE-KMS**                | AWS KMS                   | Key control + audit              |
| **SSE-C**                  | Customer supplies key     | Customer sends key with requests |
| **Client-side encryption** | Customer                  | Encrypt before upload            |

### SSE-S3

The simplest option.

Use when:

> "Encrypt the S3 objects."

without requiring special key management.

---

## SSE-KMS

Uses AWS KMS.

Advantages:

* Customer-managed key option
* Fine-grained permissions
* Key rotation controls
* KMS audit trail through CloudTrail

### Exam signal

> "Security team must audit use of the encryption key."

→ **SSE-KMS**

### S3 Bucket Key

When using SSE-KMS, large numbers of objects can cause many KMS requests.

**S3 Bucket Keys** reduce the number of KMS requests made by S3 and can significantly reduce request costs.

Trade-off:

> Fewer KMS operations means a less granular KMS/CloudTrail audit trail.

### Exam signal

> "SSE-KMS costs are too high because there are millions of S3 objects."

→ **S3 Bucket Key**

---

# SSE-C

With SSE-C:

> You provide the encryption key with each request.

AWS performs the encryption/decryption, but AWS does not store the customer-provided key for you.

HTTPS is required.

### Exam signal

> "Customer wants to provide and manage the encryption key for every request."

→ **SSE-C**

---

# Client-side encryption

With client-side encryption:

```text
Your application
      ↓
Encrypt
      ↓
Ciphertext
      ↓
S3
```

S3 never receives the original plaintext.

### Exam signal

> "Data must be encrypted before it reaches AWS."

→ **Client-side encryption**

---

# Encryption in transit

Encryption at rest and encryption in transit are different.

### At rest

Protects stored data:

```text
S3 object
→ SSE-S3 / SSE-KMS / SSE-C / client-side
```

### In transit

Protects network traffic:

```text
Client
  ↓
HTTPS / TLS
  ↓
S3
```

### Enforce HTTPS

Use an S3 bucket policy that denies requests when:

```text
aws:SecureTransport = false
```

### Exam signal

> "All S3 traffic must use HTTPS."

→ **Deny `aws:SecureTransport = false`**

---

# Encrypting existing objects

Enabling encryption does not retroactively transform previously stored objects.

To change existing objects, use an operation that rewrites them with encryption, such as **S3 Batch Operations**.

### Exam signal

> "Encrypt all existing unencrypted S3 objects."

→ **S3 Batch Operations**

---

# Access control

## Block Public Access

S3 Block Public Access is the main protection against accidental public exposure.

It can block public access even when a bucket policy or ACL attempts to grant it.

### Exam signal

> "Bucket policy allows public access, but the objects are still not public."

→ **Block Public Access**

---

# Bucket policies

A bucket policy is a **resource-based policy**.

It can control:

* Who can access the bucket
* Cross-account access
* Require HTTPS
* Require encryption
* Restrict access by IP or other conditions

This connects directly to the IAM concepts from Section 1.

---

# Presigned URLs

A presigned URL provides temporary access to a private S3 object.

Typical scenario:

```text
Customer
   ↓
Temporary signed URL
   ↓
Private S3 object
```

The URL uses the permissions of the principal that created it.

### Exam signal

> "Allow a customer to download a private object for a limited time without giving them AWS credentials."

→ **Presigned URL**

---

# CloudFront + S3: OAC

**Origin Access Control (OAC)** restricts access to an S3 bucket so that CloudFront can retrieve the objects.

Architecture:

```text
User
 ↓
CloudFront
 ↓
S3
```

Use OAC when:

> "Users should access content through CloudFront and not directly through S3."

OAC is preferred over the older **Origin Access Identity (OAI)** approach.

---

# S3 access logs vs CloudTrail

These answer different questions.

|                 | S3 Server Access Logs   | CloudTrail data events        |
| --------------- | ----------------------- | ----------------------------- |
| Main purpose    | Request logging         | AWS API activity              |
| Identity detail | Less rich               | Rich identity information     |
| Delivery        | Best effort / delayed   | Near real-time                |
| Cost            | Storage/logging related | Charged for data events       |
| Typical use     | Detailed access logs    | Security/audit investigations |

### S3 Server Access Logs

S3 writes log files to another S3 bucket.

**Do not use the same bucket as the destination.**

Otherwise logging can create a recursive stream of log writes.

### Exam signal

> "Enable S3 access logging."

→ **Use a separate destination bucket.**

Logs can then be queried using Athena.

### CloudTrail data events

Use CloudTrail when the important question is:

> **"Which AWS principal accessed this object?"**

### Exam signal

> "Need detailed auditing of who accessed S3 objects."

→ **CloudTrail data events**

---

# S3 performance

S3 automatically scales.

For high request rates, distribute object keys across multiple prefixes so traffic is not concentrated into a small number of partitions.

A commonly tested baseline is approximately:

```text
3,500 PUT/COPY/POST/DELETE per second per prefix
5,500 GET/HEAD requests per second per prefix
```

### Exam signal

> "Application needs significantly higher S3 request throughput."

→ **Use multiple prefixes / distribute key names**

Do not confuse this with simply increasing bucket capacity. S3 storage capacity is already effectively unlimited.

---

# Multipart upload

Multipart upload divides a large object into multiple parts.

Advantages:

* Parallel uploads
* Better performance
* Failed parts can be retried independently

A single PUT cannot upload an object larger than **5 GB**.

A single S3 object can be up to **5 TB**.

Multipart upload is recommended for large objects and is required when the object exceeds the single-request size limit.

### Exam signal

> "Upload a very large file efficiently."

→ **Multipart upload**

---

# S3 Transfer Acceleration

Transfer Acceleration improves **long-distance uploads** to an S3 bucket.

Architecture:

```text
User
 ↓
Nearest AWS edge location
 ↓
AWS backbone
 ↓
S3 bucket
```

### Exam signal

> "Users around the world upload large files to one central S3 bucket."

→ **S3 Transfer Acceleration**

For global content **downloads**, think:

→ **CloudFront**

---

# Byte-range requests

A byte-range GET retrieves only part of an object.

Useful for:

* Large objects
* Parallel downloads
* Retrieving only a portion of a file

### Exam signal

> "Download only part of a large S3 object."

→ **Byte-range request**

---

# S3 event notifications

S3 can trigger actions when objects change.

Possible destinations include:

* Lambda
* SQS
* SNS
* EventBridge

Example:

```text
Image uploaded to S3
        ↓
S3 event
        ↓
Lambda
        ↓
Generate thumbnail
```

### EventBridge

EventBridge is useful when you need richer event filtering or more complex fan-out and routing.

### Exam signal

> "When a file is uploaded, automatically process it."

→ **S3 Event Notification**

---

# S3 Select vs Athena

Both can query data in S3, but they are different.

## S3 Select

Queries **one object** and returns only the required data.

```text
One large CSV
   ↓
S3 Select
   ↓
matching rows
```

### Exam signal

> "Retrieve only part of one large CSV/JSON object."

→ **S3 Select**

## Athena

Queries data across **many S3 objects / datasets** using SQL.

```text
Many S3 files
      ↓
    Athena
      ↓
     SQL
```

### Exam signal

> "Analyze logs stored across many S3 files."

→ **Athena**

# The most important SAA decision tree

When you see an S3 question, first identify the problem.

```text
What is the question asking?
│
├── Storage cost / access pattern
│      ↓
│   Storage classes
│
├── Known schedule
│      ↓
│   Lifecycle
│
├── Unknown access pattern
│      ↓
│   Intelligent-Tiering
│
├── Accidental deletion / overwrite
│      ↓
│   Versioning
│
├── "Nobody can delete for X years"
│      ↓
│   Object Lock
│
│   ├── Fixed period
│   │      ↓
│   │   Retention period
│   │
│   ├── Legal case / no fixed end
│   │      ↓
│   │   Legal Hold
│   │
│   ├── Admins can bypass
│   │      ↓
│   │   Governance
│   │
│   └── Nobody can bypass
│          ↓
│       Compliance
│
├── Cross-Region copy
│      ↓
│   CRR
│
├── Encryption
```

# The four Object Lock answers — memorize this

This is the exact pattern from the compliance question:

```text
                 S3 Object Lock
                       │
          ┌────────────┴────────────┐
          │                         │
      Governance               Compliance
          │                         │
   Can bypass with          Cannot bypass during
special permission          retention period
          │                         │
          └────────────┬────────────┘
                       │
              What type of protection?
                       │
              ┌────────┴────────┐
              │                 │
       Retention period      Legal Hold
              │                 │
       Fixed duration       Until explicitly
       1 year / 5 years      released
              │                 │
              └────────┬────────┘
                       │
                       ▼
       "One year + even root cannot delete"
                       ↓
        COMPLIANCE + RETENTION PERIOD
```

### Answer-choice traps

| Answer choice                         | Why                                                                                 |
| ------------------------------------- | ----------------------------------------------------------------------------------- |
| **Compliance + legal hold**           | Wrong: legal hold is for an ongoing hold, not the normal fixed one-year requirement |
| ✅ **Compliance + one-year retention** | **Correct**                                                                         |
| **Governance + legal hold**           | Wrong: governance can be bypassed by authorized users                               |
| **Governance + one-year retention**   | Wrong: fixed period is correct, but governance is not strong enough                 |

The highest-value SAA memory for this topic is:

> **Fixed period → Retention.**
> **Legal case / indefinite → Legal Hold.**
> **Can bypass → Governance.**
> **Cannot bypass, even administrators/root → Compliance.**

S3 is fundamentally about choosing the right **storage class, protection mechanism, access method, and integration pattern**. Once you identify which of those four problems the question is describing, most S3 questions become straightforward.
