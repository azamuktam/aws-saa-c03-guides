# Section 2: S3 — Simple Storage Service

## The idea

**Amazon S3 (Simple Storage Service)** is **object storage**.

```text
Bucket
  ↓
Object
  ├── Data
  ├── Key
  └── Metadata
```

S3 is not:

* Block storage → **EBS**
* Shared filesystem → **EFS / FSx**

You normally replace an entire object rather than modify individual bytes.

### Important S3 facts

* **99.999999999% durability**
* Bucket belongs to **one Region**
* Bucket names are **globally unique**
* Max object size: **5 TB**
* S3 has effectively **unlimited total storage**

### S3 key

```text
photos/2026/cat.jpg
```

S3 has no traditional folders; `photos/2026/` is part of the key.

---

# S3 storage classes

| Storage class                  | Access pattern            | Retrieval                    | Minimum storage |
| ------------------------------ | ------------------------- | ---------------------------- | --------------- |
| **S3 Standard**                | Frequent                  | Milliseconds                 | None            |
| **Intelligent-Tiering**        | Unknown/changing          | Milliseconds in active tiers | None            |
| **Standard-IA**                | Infrequent                | Milliseconds                 | 30 days         |
| **One Zone-IA**                | Infrequent + re-creatable | Milliseconds                 | 30 days         |
| **Glacier Instant Retrieval**  | Rare + immediate          | Milliseconds                 | 90 days         |
| **Glacier Flexible Retrieval** | Archive                   | Minutes–hours                | 90 days         |
| **Glacier Deep Archive**       | Very rare / long-term     | Hours                        | 180 days        |

Glacier classes provide the same high durability model as S3 Standard with lower storage cost.

## 3-filter method

### 1. Access frequency

```text
Frequent
→ Standard

Unknown / unpredictable
→ Intelligent-Tiering

Infrequent
→ Standard-IA / One Zone-IA

Rare
→ Glacier
```

### 2. Retrieval speed

```text
Milliseconds
→ Standard / Standard-IA / One Zone-IA / Glacier Instant

Minutes–hours
→ Glacier Flexible

Hours acceptable
→ Deep Archive
```

### 3. Retention

```text
Standard-IA     → 30 days
One Zone-IA     → 30 days
Glacier Instant → 90 days
Glacier Flexible→ 90 days
Deep Archive    → 180 days
```

Deleting/transitioning before the minimum duration can still incur charges for the remaining minimum period.

# S3 Standard

Use for:

* Frequently accessed data
* Low-latency access
* Predictable access

> Frequently accessed → **S3 Standard**

---

# S3 Intelligent-Tiering

Use when access is **unknown or unpredictable**.

S3 automatically moves objects between access tiers. There is a small monitoring/automation charge.

```text
Known access schedule
→ Lifecycle

Unknown/unpredictable access
→ Intelligent-Tiering
```

---

# S3 Standard-IA

Use for:

* Infrequent access
* Immediate retrieval
* Multi-AZ resilience

> Infrequent + immediate → **Standard-IA**

---

# S3 One Zone-IA

Stores data in **one AZ**.

Use for:

* Infrequent access
* Re-creatable data
* Secondary copies

> Re-creatable / secondary copy → **One Zone-IA**

Do not use it as the only copy of irreplaceable data.

---

# S3 Glacier Instant Retrieval

For:

* Rarely accessed data
* Immediate retrieval
* Millisecond access

> Rare + immediate retrieval → **Glacier Instant Retrieval**

---

# S3 Glacier Flexible Retrieval

For archival data where retrieval can take **minutes to hours**.

> Archive + minutes/hours acceptable → **Glacier Flexible Retrieval**

### Retrieval options

| Retrieval     |   Typical time | Use                       |
| ------------- | -------------: | ------------------------- |
| **Expedited** |    **1–5 min** | Urgent access             |
| **Standard**  |  **3–5 hours** | Normal retrieval          |
| **Bulk**      | **5–12 hours** | Large, low-cost retrieval |

**Provisioned Retrieval Capacity** guarantees capacity for **Expedited** retrievals and provides up to **300 MB/s per capacity unit**.

> Under 15-minute retrieval → **Expedited**

> Guaranteed Expedited capacity / predictable fast retrieval → **Provisioned Retrieval Capacity**

> Large amount + lowest retrieval cost → **Bulk**

---

# S3 Glacier Deep Archive

For very long-term archival:

* Regulatory records
* Compliance archives
* Multi-year retention
* Very rare access

Lowest-cost S3 storage class; retrieval takes hours.

> Cheapest long-term archive → **Deep Archive**

# Lifecycle rules

Automatically:

* Transition objects

```text
Standard
   ↓
Standard-IA
   ↓
Glacier
```

# Versioning

Keeps multiple object versions.

```text
Version 1
Version 2
```

A normal delete on a versioned bucket creates a **delete marker** rather than immediately deleting the current version.

```text
Delete Marker
Version 2
Version 1
```

Remove the delete marker and the object becomes visible again.

### Important

Once Versioning is enabled, it can be **suspended**, but the bucket cannot return to its original unversioned state.

> Accidental overwrite/deletion protection → **Versioning**

---

# Delete marker

With Versioning enabled:

```text
DELETE object
→ Delete Marker created
→ Old versions remain
```

But:

```text
DELETE object?versionId=...
→ Specific version permanently deleted
```

Important event distinction:

```text
Delete marker
→ s3:ObjectRemoved:DeleteMarkerCreated

Permanent deletion
→ s3:ObjectRemoved:Delete
```

---

# MFA Delete

Adds MFA protection to certain Versioning operations.

Useful against:

* Permanent deletion of object versions
* Malicious deletion
* Accidental versioning suspension

> Require MFA before permanently deleting versions → **MFA Delete**

---

# S3 Object Lock — WORM

**WORM = Write Once, Read Many**

Object Lock prevents protected object versions from being overwritten/deleted during the protection period.

Object Lock requires Versioning.

```text
S3
 ↓
Versioning
 ↓
Object Lock
```

---

# Object Lock: Governance vs Compliance

|                              | **Governance**                               | **Compliance** |
| ---------------------------- | -------------------------------------------- | -------------- |
| Normal users can delete?     | No                                           | No             |
| Authorized users can bypass? | **Yes**                                      | **No**         |
| Strict immutability          | Less suitable                                | **Yes**        |
| Admin/root bypass            | Possible with appropriate bypass permissions | **No**         |

### Governance

Can be bypassed with **`s3:BypassGovernanceRetention`**.

> Administrators may override → **Governance**

### Compliance

Cannot be bypassed during retention, including by administrators/root.

> Nobody can bypass → **Compliance**

---

# Retention period vs Legal Hold

### Retention period

Protect until a **specific date**.

> "Keep for exactly 5 years." → **Retention period**

### Legal Hold

Protection remains until explicitly removed.

> Litigation / investigation / case closure → **Legal Hold**

---

# Object Lock vs Versioning

```text
Recover old version after accidental deletion
→ Versioning

Prevent deletion/overwrite during retention
→ Object Lock
```

---

# Object Lock and replication

For locked-object replication:

* Source and destination must have Object Lock enabled.
* Retention metadata can be replicated.

Useful for compliance copies in another bucket/Region.

# Replication

## Cross-Region Replication (CRR)

Copies objects to another Region.

Uses:

* Disaster recovery
* Compliance
* Geographic separation
* Lower latency

```text
Region A
   ↓ CRR
Region B
```

## Same-Region Replication (SRR)

Copies objects to another bucket in the same Region.

Uses:

* Log aggregation
* Production → test
* Separate accounts/buckets
* Data isolation

### Requirement

Standard replication requires **Versioning on both source and destination**.

### Existing objects

> Existing objects need replication → **S3 Batch Replication**

# Encryption

S3 encrypts new objects by default.

| Encryption      | Key management | Signal                        |
| --------------- | -------------- | ----------------------------- |
| **SSE-S3**      | AWS            | Simple server-side encryption |
| **SSE-KMS**     | AWS KMS        | Key control + audit           |
| **SSE-C**       | Customer       | Customer supplies key         |
| **Client-side** | Customer       | Encrypt before upload         |

## SSE-S3

Use for simple S3 encryption without special key-management requirements.

## SSE-KMS

Provides:

* Customer-managed KMS key option
* Fine-grained permissions
* Key controls
* CloudTrail audit

> Need to audit encryption-key usage → **SSE-KMS**

### S3 Bucket Key

Reduces KMS requests and costs for large numbers of SSE-KMS objects.

Trade-off: less granular KMS/CloudTrail visibility.

> Too many KMS requests/cost → **S3 Bucket Key**

## SSE-C

Customer supplies the key with each request. HTTPS is required.

> Customer manages key for each request → **SSE-C**

## Client-side encryption

```text
Application
 ↓ encrypt
Ciphertext
 ↓
S3
```

> Must encrypt before AWS receives the data → **Client-side encryption**

---

# Encryption in transit

At rest:

```text
SSE-S3 / SSE-KMS / SSE-C / Client-side
```

In transit:

```text
HTTPS / TLS
```

Force HTTPS with a bucket policy denying:

```text
aws:SecureTransport = false
```

> Force HTTPS → **`aws:SecureTransport`**

# VPC Endpoint Policy for S3

An **S3 Gateway VPC Endpoint** provides private VPC access to S3 without an Internet Gateway or NAT Gateway.

A **VPC endpoint policy** controls what can be accessed **through that specific endpoint**.

```text
VPC
 ↓
S3 Gateway Endpoint
 ↓
Endpoint policy
 ↓
Approved S3 buckets
```

Different endpoints have different policies.

> EC2 can access only specific S3 buckets through an S3 gateway endpoint → **Gateway VPC Endpoint + endpoint policy**

### Important distinction

```text
VPC endpoint policy
→ controls access THROUGH the endpoint

Bucket policy
→ controls access TO the bucket
```

---

# Bucket policies

Resource-based policies controlling:

* Who can access
* Cross-account access
* HTTPS
* Encryption
* IP restrictions
* VPC endpoint restrictions

`aws:sourceVpce` can restrict access to a specific VPC endpoint.

> Bucket only accessible through a specific endpoint → **Bucket policy + `aws:sourceVpce`**

Main protection against accidental public exposure.

# CloudFront + S3: OAC

**Origin Access Control (OAC)** lets CloudFront access the S3 origin while preventing direct public S3 access.

```text
User
 ↓
CloudFront
 ↓
S3
```

> Users access content through CloudFront, not directly through S3 → **OAC**

OAC is preferred over the older OAI approach.

# S3 Performance

S3 automatically scales to high request rates.

### Per-prefix baseline

| Operation                      |               Per prefix |
| ------------------------------ | -----------------------: |
| **PUT / COPY / POST / DELETE** | **≥ 3,500 requests/sec** |
| **GET / HEAD**                 | **≥ 5,500 requests/sec** |

There is **no limit on the number of prefixes in a bucket**.

### What is a prefix?

A prefix is the beginning of an S3 object key.

```text
photos/2026/cat.jpg
```

Possible prefix:

```text
photos/
```

> **Prefix = part of the object key, not a real folder.**

### High request rates

To increase aggregate request throughput:

```text
Multiple prefixes
      +
Parallel requests
      ↓
Higher aggregate throughput
```

Example:

```text
1 prefix  → 5,500 GET/sec
10 prefixes → potentially 55,000 GET/sec
```

### Important

S3 automatically scales, so you do **not** normally need to create prefixes manually. For very high request rates, distributing requests across prefixes can improve performance.

A sudden large increase in traffic can temporarily cause:

```text
503 Slow Down
```

→ retry using **exponential backoff**.

### SAA memory

> **3,500 writes / 5,500 reads per prefix**

> **Need more → distribute across multiple prefixes**

# Multipart upload

Splits large objects into parts.

Benefits:

* Parallel uploads
* Better performance
* Retry individual parts

Limits:

* Single PUT: **5 GB**
* Max object: **5 TB**

> Upload a very large file efficiently → **Multipart upload**

# S3 Event Notifications

**S3 Event Notifications = trigger actions when objects change.**

```text
SQS         → queue
SNS         → notification / fan-out
Lambda      → run code
EventBridge → advanced routing
```

### Important events

| Event                                  | Meaning                               |
| -------------------------------------- | ------------------------------------- |
| `s3:ObjectCreated:*`                   | Object created                        |
| `s3:ObjectRemoved:Delete`              | Deleted / version permanently deleted |
| `s3:ObjectRemoved:DeleteMarkerCreated` | Delete marker created                 |
| `s3:ObjectRemoved:*`                   | All removal events                    |

### Exam patterns

> New object → `s3:ObjectCreated:*`

> Permanent deletion → `s3:ObjectRemoved:Delete`

> Delete marker → `s3:ObjectRemoved:DeleteMarkerCreated`

> All removals → `s3:ObjectRemoved:*`

> Queue processing → **SQS**

> Notify/fan-out → **SNS**

> Complex routing → **EventBridge**

### Trap

```text
DELETE on versioned bucket
→ Delete marker
→ NOT permanent deletion

DELETE specific version ID
→ Permanent deletion
```

### Pocket card

```text
Object created → ObjectCreated:*
Permanent delete → ObjectRemoved:Delete
Delete marker → ObjectRemoved:DeleteMarkerCreated
All removals → ObjectRemoved:*
Queue → SQS
Notify → SNS
Complex routing → EventBridge
```

# S3 Select vs Athena

## S3 Select

Queries **one object** and returns only matching data.

> Part of one large CSV/JSON → **S3 Select**

## Athena

Queries **many S3 objects/datasets** using SQL.

> Analyze many S3 files → **Athena**
