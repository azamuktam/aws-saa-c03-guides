# Section 2: S3 — Simple Storage Service

## The idea

**Amazon S3 (Simple Storage Service)** is **object storage**.

```text
Bucket
  ↓
Object
  ├── Data
  ├── Key
  └── Metadata
```

S3 is not:

* Block storage → **EBS**
* Shared filesystem → **EFS / FSx**

You normally replace an entire object rather than modify individual bytes.

### Important S3 facts

* **99.999999999% durability**
* Bucket belongs to **one Region**
* Bucket names are **globally unique**
* Max object size: **5 TB**
* S3 has effectively **unlimited total storage**

### S3 key

```text
photos/2026/cat.jpg
```

S3 has no traditional folders; `photos/2026/` is part of the key.

# S3 static website + Route 53

S3 can host a **static website** containing:

* HTML
* CSS
* JavaScript
* Images
* Other static files

For a custom domain, Route 53 can route traffic to the S3 **website endpoint**.

### Important bucket-name rule

When routing a domain directly to an S3 bucket configured for **static website hosting**, the:

> **S3 bucket name must exactly match the domain or subdomain being routed.**

Example:

```text
Domain:
example.com

Bucket:
example.com
```

For a subdomain:

```text
Domain:
www.example.com

Bucket:
www.example.com
```

This is a common SAA exam requirement.

### Typical architecture

```text
User
  ↓
Route 53
  ↓
A / Alias record
  ↓
S3 website endpoint
  ↓
S3 bucket
```

### Important Route 53 prerequisites

For the direct S3 website-endpoint pattern:

* A **registered domain name**
* An S3 bucket configured for **static website hosting**
* The **bucket name matches the domain/subdomain**
* Route 53 is hosting the DNS for the domain
* Use a Route 53 **A Alias** record pointing to the S3 website endpoint

Route 53 alias records can be used for both:

```text
example.com
www.example.com
```

The S3 bucket must match the record name used for the S3 website target.

### Region misconception

The S3 bucket does **not** have to be in the same Region as the Route 53 hosted zone.

Route 53 is a global DNS service.

You select the **S3 bucket's Region** when configuring the S3 website endpoint as the alias target.

### CORS misconception

**CORS is not required simply to route Route 53 traffic to an S3 website.**

```text
Route 53
→ DNS routing

CORS
→ Browser cross-origin access
```

Do not confuse the two.

### Important HTTPS caveat

An S3 **website endpoint does not support SSL/TLS directly**.

For HTTPS, a common architecture is:

```text
User
  ↓ HTTPS
CloudFront
  ↓
S3
```

With CloudFront, you can use a custom certificate and keep the S3 bucket behind CloudFront.

### Important distinction

The bucket-name-must-match-domain rule applies to the **direct S3 website endpoint** pattern.

It does **not** mean every S3 bucket behind CloudFront must have the same name as the user's domain.

For example:

```text
example.com
    ↓
CloudFront
    ↓
my-company-static-assets-123
```

The CloudFront distribution can use a differently named S3 bucket as its origin.

> **Direct Route 53 → S3 website endpoint → bucket name matches domain**

> **CloudFront → S3 origin → bucket name does not need to match the public domain**

# S3 storage classes

| Storage class                  | Access pattern            | Retrieval                    | Minimum storage |
| ------------------------------ | ------------------------- | ---------------------------- | --------------- |
| **S3 Standard**                | Frequent                  | Milliseconds                 | None            |
| **Intelligent-Tiering**        | Unknown/changing          | Milliseconds in active tiers | None            |
| **Standard-IA**                | Infrequent                | Milliseconds                 | 30 days         |
| **One Zone-IA**                | Infrequent + re-creatable | Milliseconds                 | 30 days         |
| **Glacier Instant Retrieval**  | Rare + immediate          | Milliseconds                 | 90 days         |
| **Glacier Flexible Retrieval** | Archive                   | Minutes–hours                | 90 days         |
| **Glacier Deep Archive**       | Very rare / long-term     | Hours                        | 180 days        |

Glacier classes provide the same high durability model as S3 Standard with lower storage cost.

## 3-filter method

### 1. Access frequency

```text
Frequent
→ Standard

Unknown / unpredictable
→ Intelligent-Tiering

Infrequent
→ Standard-IA / One Zone-IA

Rare
→ Glacier
```

### 2. Retrieval speed

```text
Milliseconds
→ Standard / Standard-IA / One Zone-IA / Glacier Instant

Minutes–hours
→ Glacier Flexible

Hours acceptable
→ Deep Archive
```

### 3. Retention

```text
Standard-IA     → 30 days
One Zone-IA     → 30 days
Glacier Instant → 90 days
Glacier Flexible→ 90 days
Deep Archive    → 180 days
```

Deleting/transitioning before the minimum duration can still incur charges for the remaining minimum period.

Use for:

* Infrequent access
* Immediate retrieval
* Multi-AZ resilience

> Infrequent + immediate → **Standard-IA**

# S3 One Zone-IA

Stores data in **one AZ**.

Use for:

* Infrequent access
* Re-creatable data
* Secondary copies

> Re-creatable / secondary copy → **One Zone-IA**

Do not use it as the only copy of irreplaceable data.

---

# S3 Glacier Instant Retrieval

For:

* Rarely accessed data
* Immediate retrieval
* Millisecond access

> Rare + immediate retrieval → **Glacier Instant Retrieval**

---

# S3 Glacier Flexible Retrieval

For archival data where retrieval can take **minutes to hours**.

> Archive + minutes/hours acceptable → **Glacier Flexible Retrieval**

### Retrieval options

| Retrieval     |   Typical time | Use                       |
| ------------- | -------------: | ------------------------- |
| **Expedited** |    **1–5 min** | Urgent access             |
| **Standard**  |  **3–5 hours** | Normal retrieval          |
| **Bulk**      | **5–12 hours** | Large, low-cost retrieval |

**Provisioned Retrieval Capacity** guarantees capacity for **Expedited** retrievals and provides up to **300 MB/s per capacity unit**.

> Under 15-minute retrieval → **Expedited**

> Guaranteed Expedited capacity / predictable fast retrieval → **Provisioned Retrieval Capacity**

> Large amount + lowest retrieval cost → **Bulk**

---

# S3 Glacier Deep Archive

For very long-term archival:

* Regulatory records
* Compliance archives
* Multi-year retention
* Very rare access

Lowest-cost S3 storage class; retrieval takes hours.

> Cheapest long-term archive → **Deep Archive**

# Versioning

Keeps multiple object versions.

```text
Version 1
Version 2
```

A normal delete on a versioned bucket creates a **delete marker** rather than immediately deleting the current version.

```text
Delete Marker
Version 2
Version 1
```

Remove the delete marker and the object becomes visible again.

### Important

Once Versioning is enabled, it can be **suspended**, but the bucket cannot return to its original unversioned state.

> Accidental overwrite/deletion protection → **Versioning**

---

# Delete marker

With Versioning enabled:

```text
DELETE object
→ Delete Marker created
→ Old versions remain
```

But:

```text
DELETE object?versionId=...
→ Specific version permanently deleted
```

Important event distinction:

```text
Delete marker
→ s3:ObjectRemoved:DeleteMarkerCreated

Permanent deletion
→ s3:ObjectRemoved:Delete
```

---

# MFA Delete

Adds MFA protection to certain Versioning operations.

Useful against:

* Permanent deletion of object versions
* Malicious deletion
* Accidental versioning suspension

> Require MFA before permanently deleting versions → **MFA Delete**

# S3 Object Lock — WORM

**WORM = Write Once, Read Many**

Object Lock prevents protected object versions from being overwritten/deleted during the protection period.

Object Lock requires Versioning.

```text
S3
 ↓
Versioning
 ↓
Object Lock
```

---

# Object Lock: Governance vs Compliance

|                              | **Governance**                               | **Compliance** |
| ---------------------------- | -------------------------------------------- | -------------- |
| Normal users can delete?     | No                                           | No             |
| Authorized users can bypass? | **Yes**                                      | **No**         |
| Strict immutability          | Less suitable                                | **Yes**        |
| Admin/root bypass            | Possible with appropriate bypass permissions | **No**         |

### Governance

Can be bypassed with **`s3:BypassGovernanceRetention`**.

> Administrators may override → **Governance**

### Compliance

Cannot be bypassed during retention, including by administrators/root.

> Nobody can bypass → **Compliance**

---

# Retention period vs Legal Hold

### Retention period

Protect until a **specific date**.

> "Keep for exactly 5 years." → **Retention period**

### Legal Hold

Protection remains until explicitly removed.

> Litigation / investigation / case closure → **Legal Hold**

---

# Object Lock vs Versioning

```text
Recover old version after accidental deletion
→ Versioning

Prevent deletion/overwrite during retention
→ Object Lock
```

# Replication

## Cross-Region Replication (CRR)

Copies objects to another Region.

Uses:

* Disaster recovery
* Compliance
* Geographic separation
* Lower latency

```text
Region A
   ↓ CRR
Region B
```

## Same-Region Replication (SRR)

Copies objects to another bucket in the same Region.

Uses:

* Log aggregation
* Production → test
* Separate accounts/buckets
* Data isolation

### Requirement

Standard replication requires **Versioning on both source and destination**.

### Existing objects

> Existing objects need replication → **S3 Batch Replication**

# Encryption

S3 encrypts new objects by default.

| Encryption      | Key management | Signal                        |
| --------------- | -------------- | ----------------------------- |
| **SSE-S3**      | AWS            | Simple server-side encryption |
| **SSE-KMS**     | AWS KMS        | Key control + audit           |
| **SSE-C**       | Customer       | Customer supplies key         |
| **Client-side** | Customer       | Encrypt before upload         |

## SSE-S3

Use for simple S3 encryption without special key-management requirements.

## SSE-KMS

Provides:

* Customer-managed KMS key option
* Fine-grained permissions
* Key controls
* CloudTrail audit

> Need to audit encryption-key usage → **SSE-KMS**

### S3 Bucket Key

Reduces KMS requests and costs for large numbers of SSE-KMS objects.

Trade-off: less granular KMS/CloudTrail visibility.

> Too many KMS requests/cost → **S3 Bucket Key**

## SSE-C

Customer supplies the key with each request. HTTPS is required.

> Customer manages key for each request → **SSE-C**

## Client-side encryption

```text
Application
 ↓ encrypt
Ciphertext
 ↓
S3
```

> Must encrypt before AWS receives the data → **Client-side encryption**

# VPC Endpoint Policy for S3

An **S3 Gateway VPC Endpoint** provides private VPC access to S3 without an Internet Gateway or NAT Gateway.

A **VPC endpoint policy** controls what can be accessed **through that specific endpoint**.

```text
VPC
 ↓
S3 Gateway Endpoint
 ↓
Endpoint policy
 ↓
Approved S3 buckets
```

Different endpoints have different policies.

> EC2 can access only specific S3 buckets through an S3 gateway endpoint → **Gateway VPC Endpoint + endpoint policy**

### Important distinction

```text
VPC endpoint policy
→ controls access THROUGH the endpoint

Bucket policy
→ controls access TO the bucket
```

Resource-based policies controlling:

* Who can access

* Encryption
* IP restrictions
* VPC endpoint restrictions

`aws:sourceVpce` can restrict access to a specific VPC endpoint.

> Bucket only accessible through a specific endpoint → **Bucket policy + `aws:sourceVpce`**

# S3 Requester Pays

Used when you share an S3 dataset with other AWS accounts and want the **requester to pay the S3 request and applicable data-transfer/retrieval charges** instead of the bucket owner.

```text
Bucket owner
→ Pays for storage

Requester
→ Pays for requests
→ Pays for applicable data transfer/retrieval charges
```

Useful for:

* Large datasets shared with other AWS accounts
* Public/shared datasets where the owner does not want to pay access costs
* Cross-account data downloads

### Important

Requester Pays **does not grant access by itself**.

The requester must still have permission to access the bucket, such as through:

* IAM policies
* Bucket policies
* Cross-account permissions

Requester Pays requires authenticated requests, so **anonymous requests are not allowed**.

### Key distinction

```text
Cross-account access
→ Who is allowed to access the bucket?

Requester Pays
→ Who pays for the request/download?
```

You may need **both** when sharing data with another AWS account.

> Large S3 dataset shared with another account + requester should pay access/download costs → **S3 Requester Pays**

# Public S3 objects

To make S3 objects readable by anyone on the Internet:

```text
Bucket policy
→ Allow s3:GetObject
→ Principal: "*"
```

A **public-read object ACL** can also make an object public **when ACLs are enabled**, but modern S3 buckets usually use **Bucket owner enforced**, which disables ACLs.

### Important

```text
Bucket policy / public-read ACL
→ controls whether the object is public

CORS
→ controls whether browser JavaScript can access a cross-origin response
```

So:

> All S3 objects must be publicly readable → **Bucket policy** or **public-read ACL if ACLs are enabled**

> CORS does NOT make S3 objects public.

### Small exam pattern

> Public static assets readable from the Internet → **Bucket policy allowing `s3:GetObject` to `Principal: "*"`**

> Public-read ACL → **possible only when ACLs are enabled**

> CORS → **not an access-control mechanism**

> Do nothing → **objects are not public by default**

# CloudFront + S3: OAC

**Origin Access Control (OAC)** lets CloudFront access the S3 origin while preventing direct public S3 access.

```text
User
 ↓
CloudFront
 ↓
S3
```

> Users access content through CloudFront, not directly through S3 → **OAC**

OAC is preferred over the older OAI approach.

### Important distinction

If CloudFront uses the **S3 REST API origin**, the S3 bucket can remain private and its name does **not** need to match the public website domain.

```text
example.com
    ↓
CloudFront
    ↓
private bucket: company-assets-123
```

Do not apply the direct S3 website-endpoint bucket-name rule to this architecture.

# S3 Performance

S3 automatically scales to high request rates.

### Per-prefix baseline

| Operation                      |               Per prefix |
| ------------------------------ | -----------------------: |
| **PUT / COPY / POST / DELETE** | **≥ 3,500 requests/sec** |
| **GET / HEAD**                 | **≥ 5,500 requests/sec** |

There is **no limit on the number of prefixes in a bucket**.

### What is a prefix?

A prefix is the beginning of an S3 object key.

```text
photos/2026/cat.jpg
```

Possible prefix:

```text
photos/
```

> **Prefix = part of the object key, not a real folder.**

### High request rates

To increase aggregate request throughput:

```text
Multiple prefixes
      +
Parallel requests
      ↓
Higher aggregate throughput
```

Example:

```text
1 prefix  → 5,500 GET/sec
10 prefixes → potentially 55,000 GET/sec
```

### Important

S3 automatically scales, so you do **not** normally need to create prefixes manually. For very high request rates, distributing requests across prefixes can improve performance.

A sudden large increase in traffic can temporarily cause:

```text
503 Slow Down
```

→ retry using **exponential backoff**.
### bucket-owner-full-control

S3 canned ACL used mainly when another AWS account uploads an object to your bucket and you want the bucket owner to have full control over that object.

Other AWS account
      ↓ uploads object
S3 bucket
      ↓
bucket-owner-full-control
      ↓
Bucket owner → FULL_CONTROL
Object writer → FULL_CONTROL

### SAA memory

> **3,500 writes / 5,500 reads per prefix**

> **Need more → distribute across multiple prefixes**

# S3 Event Notifications

**S3 Event Notifications = trigger actions when objects change.**

```text
SQS         → queue
SNS         → notification / fan-out
Lambda      → run code
EventBridge → advanced routing
```

### Important events

| Event                                  | Meaning                               |
| -------------------------------------- | ------------------------------------- |
| `s3:ObjectCreated:*`                   | Object created                        |
| `s3:ObjectRemoved:Delete`              | Deleted / version permanently deleted |
| `s3:ObjectRemoved:DeleteMarkerCreated` | Delete marker created                 |
| `s3:ObjectRemoved:*`                   | All removal events                    |

### Exam patterns

> New object → `s3:ObjectCreated:*`

> Permanent deletion → `s3:ObjectRemoved:Delete`

> Delete marker → `s3:ObjectRemoved:DeleteMarkerCreated`

> All removals → `s3:ObjectRemoved:*`

> Queue processing → **SQS**

> Notify/fan-out → **SNS**

> Complex routing → **EventBridge**

### Trap

```text
DELETE on versioned bucket
→ Delete marker
→ NOT permanent deletion

DELETE specific version ID
→ Permanent deletion
```

### Pocket card

```text
Object created → ObjectCreated:*
Permanent delete → ObjectRemoved:Delete
Delete marker → ObjectRemoved:DeleteMarkerCreated
All removals → ObjectRemoved:*
Queue → SQS
Notify → SNS
Complex routing → EventBridge
```

> → **Amazon EventBridge**

> A company needs to retrieve only matching rows from a single large CSV object stored in S3. Which service is designed for this use case?
> → **S3 Select**

> A data team needs to run SQL queries across many CSV and Parquet files stored in S3 without managing servers. Which service should it use?
> → **Amazon Athena**

> A company needs urgent retrieval of archived S3 Glacier Flexible Retrieval data and wants retrieval in a few minutes. Which retrieval option should it choose?
> → **Expedited Retrieval**

> A company needs guaranteed capacity for Expedited Glacier retrievals rather than relying on on-demand capacity. What should it purchase?
> → **Provisioned Retrieval Capacity**

> A company needs to retrieve a very large amount of Glacier Flexible Retrieval data and wants the lowest retrieval cost, while waiting several hours is acceptable. Which retrieval option should it choose?
> → **Bulk Retrieval**

> A company has a static corporate website in an S3 bucket and a registered domain in Route 53. It wants Route 53 to route traffic directly to the S3 static website. Which prerequisite is required?
> → **The S3 bucket name must match the domain name.**

> A company wants to use `example.com` as the custom domain for an S3 static website hosted directly through the S3 website endpoint. What should the bucket be named?
> → **`example.com`**

> A company wants to host `www.example.com` directly from an S3 static website endpoint. What should the bucket be named?
> → **`www.example.com`**

> A company wants Route 53 to route `example.com` directly to an S3 static website. Which record type should normally be used?
> → **A Alias record pointing to the S3 website endpoint**

> A company wants to route an S3 static website through Route 53 and asks whether the Route 53 hosted zone and S3 bucket must be in the same AWS Region. What is the correct answer?
> → **No. Route 53 is global; use the S3 bucket's Region for the S3 website endpoint.**

> A company configures CORS on an S3 bucket and expects that to satisfy the prerequisite for routing a custom domain from Route 53 to the S3 website. Is CORS required?
> → **No. CORS is for browser cross-origin access, not DNS routing.**

> A company wants HTTPS for a public S3 static website using a custom domain. Can the S3 website endpoint provide HTTPS directly?
> → **No. Put CloudFront in front of S3 and use HTTPS there.**

> A company uses CloudFront in front of an S3 bucket with the public domain `example.com`. Must the S3 bucket itself be named `example.com`?
> → **No. The bucket-name matching rule applies to the direct S3 website-endpoint pattern; a CloudFront S3 origin can use a differently named bucket.**
