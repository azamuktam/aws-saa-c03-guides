# Section 3: EC2 — Elastic Compute Cloud

## The idea

Amazon EC2 lets you run virtual servers in AWS.

You choose:

* **Instance type** → CPU, memory, networking, and other hardware characteristics
* **Purchasing option** → On-Demand, Reserved Instances, Savings Plans, Spot
* **Storage** → EBS, Instance Store, or network file systems such as EFS
* **Networking** → VPC, subnet, security groups, ENIs, IP addresses

---

# EC2 instance lifecycle

| Action        | State      | RAM | Instance Store | Private IP | Elastic IP | Underlying host |
| ------------- | ---------- | --- | -------------- | ---------- | ---------- | --------------- |
| **Reboot**    | Running    | ❌   | ✅              | ✅          | ✅          | Usually same    |
| **Stop**      | Stopped    | ❌   | ❌              | ✅          | ✅          | 🔄 May change   |
| **Hibernate** | Stopped    | ✅   | ❌              | ✅          | ✅          | 🔄 May change   |
| **Terminate** | Terminated | ❌   | ❌              | ❌          | ❌*         | Removed         |


## Reboot

Reboot restarts the operating system; the EC2 instance remains the same instance.

Use it to:

* restart the OS
* restart services or recover from software problems
* avoid entering the `stopped` state

RAM is not preserved as a hibernation snapshot.

**Exam clue:** “Restart the OS without stopping the EC2 instance.” → **Reboot**

## Stop → Start

Stopping moves the instance to `stopped`; starting it again boots the OS normally.

* RAM is not preserved.
* Common for off-hours/dev-test shutdowns and applications that do not need to run continuously.
* The default public IPv4 address can change after **stop/start**.
* Use an **Elastic IP** for a persistent public IPv4 address.

**Exam clue:** “Application runs only during business hours; stop it outside those hours to reduce cost.” → **Stop**

## Hibernate

Hibernate is like stop, but preserves **RAM contents** by saving RAM state to the root EBS volume; the state is restored when the instance starts.
Hibernation **must be enabled when the EC2 instance is launched**. You cannot enable or disable hibernation after launch.
Typical clues:

* long startup time
* preserve in-memory state
* resume where the application left off
* pre-warm an application
* stop during off-hours but resume quickly

### Critical exam trap

**Hibernation must be enabled when the EC2 instance is launched.**

You **cannot enable or disable hibernation after launch**.

Therefore:

> “Enable hibernation on the existing EC2 instance.” → **Incorrect**

> “Launch/migrate the application to an EC2 instance with hibernation enabled.” → **Correct**

### Important requirements

* Available only for supported EC2 configurations.
* Root volume must be an appropriate **encrypted EBS volume** with enough capacity for the instance RAM contents.

### Cost concept

* While hibernated in `stopped`, there are no EC2 instance usage charges once it reaches `stopped`.
* Storage and other applicable resource charges still apply.
* During the hibernation transition through `stopping`, EC2 instance usage is billed.

**Exam clue:** “Stop the instance to save cost, but startup takes several minutes; resume much faster.” → **Use EC2 hibernation**

**Remember:** **Hibernation must be configured at launch.**

## Terminate

Termination permanently removes the EC2 instance; it cannot be restarted.

Storage:

* EBS volumes with **DeleteOnTermination** are deleted.
* EBS volumes configured to remain are preserved.
* **Instance Store** data is lost when the instance is stopped or terminated; it is not persistent storage.

**Exam clue:** “Permanently remove the EC2 instance.” → **Terminate**

### Lifecycle memory rule

```text
Reboot    = restart the OS
Stop      = shut down
Hibernate = shut down + preserve RAM
Terminate = delete the instance
```

## Lifecycle comparison

| Feature | Reboot | Stop/Start | Hibernate | Terminate |
|---|---:|---:|---:|---:|
| Same EC2 instance | ✅ | ✅ | ✅ | ❌ |
| OS restarts | ✅ | ✅ | ❌ | — |
| RAM preserved | ❌ | ❌ | ✅ | ❌ |
| Instance Store preserved | ✅ | ❌ | ❌ | ❌ |
| Becomes stopped | ❌ | ✅ | ✅ | ❌ |
| Can start again | ✅ | ✅ | ✅ | ❌ |
| Saves compute cost while idle | ❌ | ✅ | ✅ | — |
| Fast resume of application state | ❌ | ❌ | ✅ | ❌ |
| Permanent removal | ❌ | ❌ | ❌ | ✅ |

### Exam decision rule

```text
Restart OS
→ Reboot

Shut down temporarily / save compute cost
→ Stop

Shut down + preserve RAM + resume faster
→ Hibernate

Permanently remove
→ Terminate
```

## EC2 billing by instance state

| State | Instance usage billed? |
|---|---:|
| `pending` | ❌ |
| `running` | ✅ |
| `stopping` | ❌ |
| `stopped` | ❌ |
| `shutting-down` | ❌ |
| `terminated` | ❌ |

### Important exception: Hibernation

During hibernation, instance usage is billed while the instance is in `stopping`.

```text
Normal Stop:
running → stopping → stopped
             ❌          ❌

Hibernate:
running → stopping → stopped
             ✅          ❌
```

* **Normal stop → `stopping` = not billed**
* **Hibernate → `stopping` = billed**
* Once hibernation reaches `stopped`, EC2 instance usage charges stop; EBS storage charges still apply.

### Reserved Instance trap

A **Reserved Instance (RI) is a billing commitment**, not an EC2 instance lifecycle object.

Stopping or terminating an EC2 instance covered by an RI:

* stops that EC2 instance's usage charge
* **does not stop/cancel the RI commitment**

AWS states that Reserved Instances applied to terminated instances continue to be billed until the end of their term according to the payment option.

```text
EC2 instance stopped/terminated
→ EC2 instance usage charge stops

Reserved Instance
→ RI commitment continues
```

### Decommissioned application + unused RI

Example:

```text
Application decommissioned
→ EC2 instance no longer needed
→ Standard RI has 8 months remaining
```

Actions:

1. **Terminate the unused EC2 instance**
   * stops EC2 instance usage charges
   * do not keep an unnecessary instance running
2. **Sell the unused eligible Standard RI in the Reserved Instance Marketplace**
   * transfers the unused RI commitment after the sale
   * eligible customers can resell unused **Standard EC2 Reserved Instances**

### RI Marketplace rule

| RI type | Can be sold in RI Marketplace? |
|---|---:|
| **Eligible Standard RI** | ✅ |
| **Convertible RI** | ❌ |

Other eligibility conditions apply; not every Standard RI can necessarily be listed.

### SAA exam trap

“Application was decommissioned but the company still has Reserved Instances.”

Think:

```text
Unused EC2 instance
→ Terminate EC2 instance

Unused eligible Standard RI
→ Sell in Reserved Instance Marketplace
```

Do not choose:

* **Stop the RI** → no RI lifecycle operation like this
* **Terminate the RI** → you terminate the EC2 instance, not the RI commitment
* **Cancel the RI** → active RIs generally remain commitments for their term; eligible Standard RIs can instead be sold through the Marketplace

### Important distinction

```text
EC2 instance
= actual compute resource

Reserved Instance
= pricing commitment applied to eligible usage
```

### SAA memory rule

```text
Stop EC2
→ stops EC2 usage charges
→ RI charges continue

Terminate EC2
→ stops EC2 usage charges
→ RI commitment continues

Sell eligible Standard RI
→ transfers the RI
→ removes your RI commitment after sale
```

# Instance families

An instance type such as `m7g.2xlarge` contains:

```text
m7g.2xlarge
││ │  │
││ │  └── size
││ └───── architecture / processor family
│└─────── generation
└──────── instance family
```

## Instance family quick reference

| Type | Main use |
|---|---|
| **Storage optimized** | I/O-intensive databases, NoSQL, high disk throughput |
| **Compute optimized** | CPU-intensive applications, batch processing, HPC |
| **Memory optimized** | RAM-intensive applications, in-memory databases, caching |
| **General purpose** | Balanced workloads, web/app servers, general databases |

## Main families

| Family | Purpose | Common exam keywords |
|---|---|---|
| **M** | General purpose, balanced CPU/memory | web/app servers, general workloads |
| **T** | Burstable general purpose | occasional CPU spikes, dev/test, CPU credits |
| **C** | Compute optimized | CPU-intensive, batch, HPC |
| **R** | Memory optimized | in-memory DBs, caches, real-time analytics |
| **X** | Very high memory | SAP HANA, very large in-memory DBs |
| **I** | Storage optimized | high IOPS, low-latency local NVMe, NoSQL |
| **D** | Storage optimized, dense HDD | distributed file systems, data warehousing, large sequential datasets |
| **P** | GPU optimized | ML training, deep learning |
| **G** | GPU optimized | graphics, video rendering, ML inference |
| **Inf** | AWS Inferentia-based ML | cost-efficient ML inference |
| **Trn** | AWS Trainium-based ML | ML training |

## Graviton

A `g` suffix (`m7g`, `c7g`, `r7g`) indicates an AWS Graviton processor based on **ARM architecture**.

Typical clues:

* best price-performance
* reduce compute cost
* sustainability
* Linux/application is ARM-compatible

**Trap:** Do not choose Graviton merely because the question says “newer generation”; the workload must be ARM-compatible.

# Enhanced Networking

**Enhanced Networking** provides:

* higher bandwidth
* higher packets per second (PPS)
* consistently lower inter-instance latency
* no additional charge on supported EC2 instance types

Main technologies:

```text
ENA
→ modern / Nitro instances

EFA
→ HPC / AI/ML. + not work with t3a.medium + Windows issue
```

Older technology:

```text
Intel 82599 VF
→ older Xen-based instances
```

## ENA — Elastic Network Adapter

**ENA is the standard enhanced-networking interface for Nitro-based EC2 instances.**

Nitro EC2 → ENA → higher bandwidth, higher PPS, lower latency.

ENA also supports Windows EC2 when the required ENA driver is installed.

**Exam clue:** “Modern EC2 needs higher bandwidth, higher PPS, and lower inter-instance latency.” → **Enhanced Networking with ENA**

**Example:** A Windows app on `t3a.medium` needs higher bandwidth/PPS/lower latency → **ENA**. `t3a` is Nitro-based.

## EFA — Elastic Fabric Adapter

**EFA is specialized networking for HPC and AI/ML workloads.**

It provides very low-latency, high-throughput communication and can bypass much of the traditional OS networking stack for supported applications.

Typical use cases:

* HPC clusters
* CFD simulations
* MPI-based workloads
* tightly coupled distributed computing
* distributed AI/ML training

### EFA vs ENA

```text
ENA
= general enhanced networking
= normal VPC IP networking

EFA
= specialized HPC / AI/ML networking
= very low latency + high throughput
= OS-bypass capability for supported applications
```

EFA with ENA provides both normal IP networking and EFA capabilities on supported instances.

| Term | What it is | Key exam clue |
|---|---|---|
| **EFA** | Network interface designed for HPC | **HPC + low latency + high throughput + OS-bypass** |
| **ENA** | Enhanced networking for EC2 | General **high-performance networking**, not the specific HPC OS-bypass clue |
| **ENI** | Virtual network interface | Basic VPC networking: IPs, security groups, etc. |
| **VIF** | Virtual interface for **Direct Connect** | On-premises ↔ AWS connectivity too |

### Critical exam trap

Do **not** choose EFA merely because the question says **HPC**.

Check:

```text
HPC
→ Does the instance type support EFA?
→ Does the OS support EFA?
```

Source guide example:

> **Windows + `t3a.medium` + higher bandwidth/PPS/lower latency** → **ENA**, not EFA.

The guide states that **EFA is not supported on Windows instances**.

### Exam clues

* “HPC application requires very low-latency communication between EC2 instances.” → **EFA**
* “Improve HPC networking performance.” → **EFA**
* “Windows EC2 instance needs enhanced networking.” → **ENA**

## Cluster Placement Group + EFA

For tightly coupled HPC workloads, EFA is often combined with a **Cluster Placement Group**.

The two solve different problems:

```text
Cluster Placement Group
→ places instances close together

EFA
→ specialized high-performance networking
```

Supported families in the guide:

HPC / AI/ML

# Purchasing options

Key questions:

* How long will the workload run?
* Is usage predictable?
* Can the workload be interrupted?

| Option | Commitment | Typical use |
|---|---|---|
| **On-Demand** | None | Short-term or unpredictable workloads |
| **Reserved Instances** | 1 or 3 years | Predictable, steady EC2 usage |
| **Convertible RI** | 1 or 3 years | Predictable usage; configuration may change |
| **Savings Plans** | 1 or 3 years | Predictable spending with more flexibility |
| **Spot** | None | Interruptible, fault-tolerant workloads |
| **Dedicated Host** | Host-level allocation | Hardware visibility, certain BYOL requirements |
| **Dedicated Instance** | Dedicated hardware | Hardware isolation without host-level control |

## On-Demand

Use when:

* workload duration is uncertain
* usage is short-term
* no long-term commitment is desired
* interruption is not acceptable

**Trap:** Do not assume every workload lasting less than one year must be On-Demand. Consider whether long-term commitment makes economic and operational sense.

## Reserved Instances

Best for predictable, steady EC2 usage.

Example:

```text
Application server
→ 24 hours/day
→ 365 days/year
→ predictable capacity
```

### Standard RI

* Larger discount, less flexibility.
* Can be **sold in the Reserved Instance Marketplace** if eligibility requirements are met.

### Convertible RI

* More flexible configuration changes, smaller discount.
* Can be **exchanged** for another Convertible RI with different attributes during the term.
* **Cannot** be sold in the Reserved Instance Marketplace.

**Exam clue:** “Workload is steady, but instance family/configuration may change.” → **Convertible RI**

### Standard vs Convertible

| Feature | Standard RI | Convertible RI |
|---|---:|---:|
| Higher potential discount | ✅ | ❌ |
| Modify certain attributes | ✅ | ✅ |
| Exchange for different RI configuration | ❌ | ✅ |
| Sell in RI Marketplace | ✅ | ❌ |
| Best when | Usage predictable, config stable | Usage predictable, config may change |

## Savings Plans

Savings Plans are based on a **committed spend per hour**, not a specific instance reservation.

### Compute Savings Plan

Most flexible. Can apply across:

* EC2 instance families
* EC2 Regions
* Fargate
* Lambda

**Exam clue:** “Long-term savings + maximum flexibility to change instance families, Regions, Fargate/Lambda.” → **Compute Savings Plan**

### EC2 Instance Savings Plan

Less flexible, usually larger discount.

Commitment is tied to:

* a specific instance family
* a specific AWS Region

Example:

```text
m7i family
us-east-1
```

## Capacity reservation vs discount

A common exam trap: confusing **discounts** with **guaranteed capacity**.

A pricing commitment does not automatically reserve EC2 capacity.

Requirement:

> “Guarantee EC2 capacity in a specific Availability Zone.”

Think:

* **On-Demand Capacity Reservation**
* or a **Zonal Reserved Instance**, where applicable

A **regional RI** is primarily a billing discount and does not guarantee capacity in a particular AZ.

Savings Plans are also **billing commitments**, not capacity reservations.

## Spot Instances

Spot Instances use spare AWS capacity and can be reclaimed by AWS.

Good for interruptible workloads:

* batch processing
* image/video processing
* CI/CD workers
* distributed data processing
* stateless workers
* checkpointable workloads
* flexible background jobs

AWS provides a **two-minute interruption notice** for Spot interruptions.

Poor choice when:

* interruption is not tolerated
* application is not fault tolerant
* losing the instance causes unacceptable data loss

**Exam clue:** “Can be interrupted/restarted; minimizing cost is the priority.” → **Spot**

## Common cost pattern

For:

* predictable baseline usage
* unpredictable additional demand

a common architecture is:

```text
Predictable baseline
→ RI / Savings Plan

Additional flexible capacity
→ Spot / On-Demand
```

Example:

```text
100 instances normally required
→ 80 covered by Savings Plan
→ 20 added using Spot when possible
```

Exact combination depends on interruption tolerance.

# Dedicated Host vs Dedicated Instance

Both provide physical hardware isolation from other AWS customers.

## Dedicated Host

Provides visibility/control over the physical host.

Relevant for:

* BYOL
* per-socket licensing
* per-core licensing
* host-level visibility
* physical host placement requirements

**Exam clue:** “Software is licensed per socket or per physical core.” → **Dedicated Host**

## Dedicated Instance

Provides hardware isolation without the same host-level visibility/control.

**Exam clue:** “Only hardware isolation is required for compliance.” → **Dedicated Instance**

# Placement groups

Placement groups control how EC2 instances are placed on underlying AWS infrastructure.

| Placement group | Placement | Main goal | Typical workload | Memory |
|---|---|---|---|---|
| **Cluster** | Close together in same AZ | Low latency + high network throughput | HPC, tightly coupled workloads | **Together** |
| **Spread** | Each instance on separate underlying hardware | Individual failure isolation | Small number of critical instances | **Individuals apart** |
| **Partition** | Groups/partitions on separate underlying hardware | Group-level failure isolation | Kafka, Cassandra, Hadoop, HDFS | **Groups apart** |

## Cluster placement group

Instances are placed closely together within a single AZ.

Provides:

* very low network latency
* high network throughput

Best for:

* tightly coupled HPC
* very fast instance-to-instance communication

Trade-off:

* concentrated failure domain

**Exam clue:** “Lowest network latency between EC2 instances.” → **Cluster Placement Group**

## Elastic Fabric Adapter (EFA)

**EFA is specialized EC2 networking for HPC and AI/ML workloads.**

It provides **lower and more consistent latency and higher throughput** than traditional TCP networking for supported workloads.

Typical use cases:

* HPC clusters
* tightly coupled distributed computing
* MPI-based applications
* distributed AI/ML training

### EFA vs Cluster Placement Group

```text
Cluster Placement Group
→ puts instances close together
→ low latency / high throughput

EFA
→ specialized high-performance networking
→ HPC / AI/ML communication
```

For HPC:

```text
EC2
+
Cluster Placement Group
+
EFA
```

The guide states AWS recommends a **cluster placement group** for EFA-enabled HPC workloads, although it is not an absolute requirement for every EFA deployment.

### Multiple EFAs

Some supported multi-network-card EC2 instance types can use **multiple EFA network interfaces** to maximize network bandwidth.

Do not memorize “EFA can only be attached once.”

Instead:

> **Multiple EFAs may be possible on supported instance types, but EFA remains an HPC/AI/ML performance feature.**

### Critical exam trap

**EFA does not provide DDoS protection.**

For DDoS protection, do not choose EFA merely because the application is HPC.

```text
HPC performance
→ EFA
→ Cluster Placement Group

DDoS protection
→ AWS Shield
→ AWS WAF
→ CloudFront
→ resilient load-balanced architecture
```

### Exam clues

* “HPC application requires very low-latency communication between EC2 instances.” → **EFA**
* “Tightly coupled HPC workload requires low latency and high network throughput.” → **Cluster Placement Group + EFA**
* “Improve HPC networking performance.” → **EFA**
* “Protect a public application from DDoS attacks.” → **Shield / WAF / CloudFront**, not EFA

### Easy memory rule

```text
EFA = HPC network performance
Cluster = EC2s close together
Shield = DDoS protection
WAF = web request filtering
```

## Spread placement group

Instances are placed on distinct underlying hardware to reduce correlated hardware failures.

Best for:

* a small number of critical instances
* workloads where each instance needs an isolated failure domain

A spread placement group supports a limited number of instances per AZ.

**Exam clue:** “A few critical instances must not share the same underlying hardware.” → **Spread Placement Group**

## Partition placement group

Instances are divided into logical partitions; each partition uses separate underlying hardware.

Best for large distributed systems such as:

* Hadoop
* Cassandra
* Kafka
* HDFS

Supports large numbers of instances and provides partition information through EC2 instance metadata, allowing topology-aware applications to distribute replicas intelligently.

**Exam clue:** “Large distributed system where instances should be separated into independent hardware groups.” → **Partition Placement Group**

### Easy memory rule

```text
Cluster   = close together
Spread    = isolate individual instances
Partition = isolate groups of instances
```

### Placement group decision rule

```text
Lowest latency / highest network throughput
→ Cluster

Isolate individual instances
→ Spread

Isolate groups of instances
→ Partition
```

# Elastic Network Interface (ENI)

An **Elastic Network Interface (ENI)** is a virtual network interface attached to an EC2 instance.

A **VPC Interface Endpoint** is an AWS PrivateLink endpoint that creates ENIs inside your subnet.

An ENI can have:

* private IPv4 address
* secondary private IPv4 addresses
* IPv6 addresses
* MAC address
* security groups

Most important SAA concept: a **secondary ENI can be moved between EC2 instances**, allowing its network identity to survive an EC2 instance failure.

## Primary ENI vs Secondary ENI

Every EC2 instance has a **primary network interface**, created automatically at launch.

The primary ENI is associated with that instance and is **not used as the portable failover interface** in the typical ENI failover pattern.

Additional ENIs can be attached to an instance.

The **secondary ENI** is the failover interface because it can be **detached and attached to another compatible EC2 instance**.

### ENI failover pattern

Example:

```text
dashboard.internal.example.com
→ 10.0.1.50
→ secondary ENI
→ EC2 Instance A
```

If Instance A fails:

```text
Secondary ENI
→ detach from A
→ attach to B
```

The client keeps using `10.0.1.50`.

What moved:

```text
Secondary ENI
├── private IP
├── MAC address
├── security groups
└── other ENI configuration
```

The EC2 instance itself was replaced.

## Important ENI limitation: Availability Zone

An ENI belongs to a subnet, and a subnet belongs to one Availability Zone.

Therefore:

> **An ENI can only be attached to an instance in the same Availability Zone.**

Example:

```text
AZ-A
├── Subnet A
│   └── Secondary ENI
└── EC2 Instance A
```

The ENI can move to another instance in **AZ-A**, but not directly to an instance in AZ-B.

For **cross-AZ failover**, use mechanisms such as:

* Route 53
* Elastic Load Balancing
* application-level failover
* other multi-AZ patterns

**Exam clue:** “Primary EC2 fails and replacement must immediately use the same private IP.” → **Secondary ENI → detach → attach**

## Multiple ENIs

Multiple ENIs are useful for:

* separate network paths
* management networks
* traffic inspection appliances
* network appliances
* multi-homed instances

Example:

```text
EC2 Instance
├── ENI 1 → Application network
└── ENI 2 → Management network
```

This is a **multi-homed** configuration.

# Elastic IP address

An **Elastic IP (EIP)** is a static public IPv4 address that can be associated with an AWS resource such as an EC2 instance.

The default public IPv4 address is not persistent across **stop/start**.

**Exam clue:** “Keep the same public IPv4 after stop/start.” → **Elastic IP**

An EIP can be remapped to another EC2 instance, including one in another AZ.

## EIP vs ENI

| Feature | ENI | Elastic IP |
|---|---|---|
| Network identity | Private/network interface | Public IPv4 |
| Typical use | Private IP failover | Stable public IPv4 |
| Movable | Secondary ENI can move | Can be remapped |
| Cross-AZ | No; ENI is AZ-specific | Yes |
| Main exam use | Preserve private network identity | Preserve public IPv4 |

### Best practice

Avoid EIPs when an AWS-managed DNS/load-balancing solution is more appropriate.

Common alternatives:

* Application Load Balancer
* Network Load Balancer
* Route 53
* AWS Global Accelerator

# Instance metadata

EC2 Instance Metadata provides information about the running instance from inside the instance.

Metadata service:

```text
http://169.254.169.254/
```

Examples:

* instance ID
* Availability Zone
* local IP information
* IAM role credentials
* placement information

IMDSv2 adds session-oriented protection to the metadata service and requires a token before metadata can be requested.

**Exam clue:** “Protect the EC2 metadata service against SSRF-style attacks.” → **Require IMDSv2**

# Question patterns

## Lifecycle

> Linux OS needs to restart, but the EC2 instance must not enter `stopped`.

→ **Reboot**

> Development environment runs only 9 AM–6 PM; stop paying EC2 compute charges outside hours; no memory preservation needed.

→ **Stop → Start**

> Application takes minutes to initialize; shut it down during idle periods and restore its previous in-memory state on start.

→ **EC2 Hibernation**

**Remember:** Hibernation must be enabled when the instance is launched.

> Unused EC2 instance is no longer needed and must be permanently removed.

→ **Terminate**

## Instance families and storage

> NoSQL database already replicates data; highest priority is I/O throughput and sequential read/write performance.

→ **Storage optimized EC2 instance + Instance Store**

Why:

```text
High I/O throughput
→ Storage optimized

Database already replicates data
→ Instance Store's ephemeral nature is acceptable
```

> CPU-intensive calculations; no unusually large memory/storage requirement.

→ **Compute optimized (C family)**

> Large in-memory dataset; substantial RAM required rather than high CPU.

→ **Memory optimized (R family)**

> SAP HANA needs a very large memory footprint.

→ **X family**

> Distributed database needs very high local disk I/O and low-latency NVMe.

→ **Storage optimized (I family)**

> Large local HDD capacity; large sequential datasets.

→ **D family**

> ML workload needs GPU acceleration for training.

→ **P family**

> GPU acceleration mainly for graphics rendering or inference.

→ **G family**

> Specialized AWS hardware optimized for ML inference rather than training.

→ **Inf family**

> Linux app is ARM-compatible; wants better price-performance/lower compute cost.

→ **Graviton-based instance (`g` suffix)**

> Highly variable CPU demand; usually low but occasionally bursts significantly.

→ **T family**

> T-family instance performs well initially but later slows during sustained CPU-heavy processing.

→ **CPU credits exhausted**

> T-family workload must continue bursting beyond accumulated credits.

→ **T Unlimited**, with possible additional charges

## Networking

> Modern Nitro-based EC2 needs higher bandwidth, higher PPS, and lower inter-instance latency.

→ **Enhanced Networking with ENA**

> Tightly coupled HPC workload needs very low-latency, high-throughput communication between supported EC2 instances.

→ **Elastic Fabric Adapter (EFA)**

> Windows EC2 instance needs higher bandwidth, higher PPS, and lower inter-instance latency.

→ **ENA**, not EFA

> Older Xen-based EC2 from a supported family needs enhanced networking.

→ **Intel 82599 VF**

> Tightly coupled HPC cluster needs very low network latency and high network throughput.

→ **Cluster Placement Group**

For the strongest HPC networking setup:

→ **Cluster Placement Group + EFA**

## Placement groups

> Small number of critical EC2 instances; each must be on separate underlying hardware.

→ **Spread Placement Group**

> Large Kafka cluster must separate groups of brokers across independent hardware failure domains.

→ **Partition Placement Group**

> Tightly coupled distributed application needs the lowest possible network latency between EC2 instances.

→ **Cluster Placement Group**

## Purchasing and cost

> Batch workload can be interrupted/restarted; minimizing EC2 cost is highest priority.

→ **Spot Instances**

> Production workload cannot tolerate interruption and needs predictable compute capacity.

→ **Do not use Spot.** Consider **On-Demand**, **Reserved Instances**, or **Savings Plans** based on usage and commitment needs.

> Predictable EC2 usage but instance configuration may change during the commitment.

→ **Convertible Reserved Instance**

> Predictable EC2 usage; wants larger potential discount; no need to exchange RI configuration.

→ **Standard Reserved Instance**

> Long-term savings with maximum flexibility across instance families, Regions, EC2, Fargate, and Lambda.

→ **Compute Savings Plan**

> Long-term commitment tied to one EC2 instance family in one AWS Region.

→ **EC2 Instance Savings Plan**

> EC2 capacity must be guaranteed in a specific AZ.

→ **On-Demand Capacity Reservation** or another appropriate zonal capacity reservation mechanism

Not merely:

→ **Regional RI or Savings Plan**

because those are primarily pricing commitments, not AZ-specific capacity reservations.

> Decommissioned application no longer needs its EC2 instance, but an eligible unused Standard RI remains.

→ **Terminate the unused EC2 instance and sell the eligible Standard RI through the Reserved Instance Marketplace**

## Dedicated hardware

> Software is licensed by physical CPU sockets/cores and physical-server visibility is required.

→ **Dedicated Host**

> Only physical hardware isolation is required for compliance; no host-level visibility/control needed.

→ **Dedicated Instance**

## ENI and IP failover

> EC2 instance fails; standby must immediately use the same private IP and security-group configuration.

→ **Move a secondary ENI to the standby instance**

> Same private IP must move from one AZ to another.

→ **Secondary ENI cannot do this because ENIs are AZ-specific.** Use a **multi-AZ DNS, load-balancing, or application-level failover architecture**.

> EC2 needs separate application and management interfaces.

→ **Multiple ENIs / multi-homed configuration**

> EC2 must keep the same public IPv4 after stop/start.

→ **Elastic IP**

> Public application needs a stable endpoint but does not specifically require a dedicated public IPv4 on the EC2 instance.

→ Prefer **Application Load Balancer, Network Load Balancer, Route 53, or Global Accelerator**, depending on the requirement.

## User data and metadata

> Install software/configuration automatically when a new EC2 instance launches.

→ **User data**

> EC2 application needs instance ID, AZ, local IP information, or IAM role credentials.

→ **Instance Metadata**

> Reduce SSRF risk against EC2 metadata service.

→ **Require IMDSv2**
