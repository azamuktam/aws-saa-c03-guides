# Section 3: EC2 — Elastic Compute Cloud

## The idea

Amazon EC2 lets you run virtual servers in AWS.

You choose:

* **Instance type** → CPU, memory, networking, and other hardware characteristics
* **Purchasing option** → On-Demand, Reserved Instances, Savings Plans, Spot
* **Storage** → EBS, Instance Store, or network file systems such as EFS
* **Networking** → VPC, subnet, security groups, Elastic Network Interfaces (ENIs), IP addresses

For SAA questions, most EC2 decisions come down to:

1. **What kind of compute resources does the workload need?**
2. **How predictable and interruptible is the workload?**
3. **How should the instance be isolated or connected?**
4. **What network identity must survive an instance failure?**
5. **What should happen when the instance needs to be restarted, paused, resumed, or removed?**

---

# EC2 instance lifecycle

| Action        | Instance state after action | RAM preserved? | Instance Store data preserved? | Main use                                                        |
| ------------- | --------------------------- | -------------: | -----------------------------: | --------------------------------------------------------------- |
| **Reboot**    | Running                     |              ❌ |                              ✅ | Restart the operating system                                    |
| **Stop**      | Stopped                     |              ❌ |                              ❌ | Shut down the instance and avoid EC2 compute charges while idle |
| **Hibernate** | Stopped                     |              ✅ |                              ❌ | Resume quickly with RAM/application state preserved             |
| **Terminate** | Terminated                  |              ❌ |                              ❌ | Permanently remove the instance                                 |

## Reboot

A reboot restarts the operating system.

The EC2 instance itself remains the same instance.

```text
RUNNING
   │
   └── Reboot
        │
        ▼
     RUNNING
```

Use reboot when:

* the OS needs to restart
* you need to restart services or recover from a software problem
* you do **not** want to stop the instance

The instance's RAM contents are not preserved as a hibernation snapshot.

### Exam clue

> "Restart the operating system without stopping the EC2 instance."

→ **Reboot**

---

## Stop → Start

Stopping an instance shuts it down and moves it to the **stopped** state.

When started again, the operating system boots normally.

```text
RUNNING
   │
   └── Stop
        │
        ▼
     STOPPED
        │
        └── Start
             │
             ▼
          RUNNING
```

A normal stop/start does **not** preserve RAM.

The instance must boot again when it is started.

Typical uses:

* save EC2 compute cost during off-hours
* shut down development/test environments
* temporarily stop an application that does not need to run continuously

### Important point

An instance's default public IPv4 address can change after a **stop/start**.

Use an **Elastic IP** when a persistent public IPv4 address is required.

### Exam clue

> "The application only runs during business hours. Stop the instance outside business hours to reduce cost."

→ **Stop the EC2 instance**

---

## Hibernate

Hibernate is similar to stopping the instance, but it preserves the **RAM contents**.

Before the instance stops:

```text
RAM
 │
 └── saved to root EBS volume
```

When the instance starts again:

```text
Root EBS
   │
   └── RAM state restored
            │
            ▼
        Application
        resumes
```

This can significantly reduce startup time because the operating system and application do not have to start from a completely clean state.

Typical exam clues:

* application has a long startup time
* preserve in-memory state
* resume where the application left off
* pre-warm an application
* stop the instance during off-hours but resume quickly

### Critical exam trap

**Hibernation must be enabled when the EC2 instance is launched.**

You **cannot enable or disable hibernation after the instance has already been launched**.

Therefore:

> "Enable hibernation on the existing EC2 instance."

→ **Incorrect**

> "Launch/migrate the application to an EC2 instance with hibernation enabled."

→ **Correct**

### Hibernation flow

```text
New EC2 instance
      │
      ▼
Launch with hibernation enabled
      │
      ▼
Start application
      │
      ▼
Fully warmed / operational
      │
      ▼
Hibernate
      │
      └── RAM saved to root EBS
               │
               ▼
          Instance stopped
               │
               ▼
             Start
               │
               ▼
       RAM state restored
               │
               ▼
        Application resumes
```

### Important requirements

Hibernation is only available for supported EC2 configurations.

The root volume must be an appropriate **encrypted EBS volume** and have enough capacity for the instance's RAM contents.

### Cost concept

While the instance is hibernated, it is in the **stopped** state, so there are no EC2 instance usage charges once it reaches `stopped`. Storage and other applicable resource charges still apply.

During the transition through `stopping` for hibernation, however, EC2 instance usage is billed.

### Exam clue

> "The company stops the instance to save cost, but startup takes several minutes."

If the requirement is to resume much faster:

→ **Use EC2 hibernation**

But remember:

> **Hibernation must be configured at launch.**

---

## Terminate

Termination permanently removes the EC2 instance.

```text
RUNNING
   │
   └── Terminate
        │
        ▼
    TERMINATED
```

After termination, the instance cannot be restarted.

The instance's compute resources are permanently released.

Be careful with storage:

* EBS volumes marked **DeleteOnTermination** are deleted when the instance terminates.
* EBS volumes configured to remain are preserved.
* **Instance Store** data is lost when the instance is stopped or terminated; it is not persistent storage.

### Exam clue

> "Permanently remove the EC2 instance."

→ **Terminate**

### Easy lifecycle memory rule

```text
Reboot    = restart the OS
Stop      = shut down
Hibernate = shut down + preserve RAM
Terminate = delete the instance
```

## Lifecycle comparison

| Feature                                   | Reboot | Stop/Start | Hibernate | Terminate |
| ----------------------------------------- | ------ | ---------- | --------- | --------- |
| Remains the same EC2 instance             | ✅      | ✅          | ✅         | ❌         |
| OS restarts                               | ✅      | ✅          | ❌         | —         |
| RAM preserved                             | ❌      | ❌          | ✅         | ❌         |
| Instance Store data preserved             | ✅      | ❌          | ❌         | ❌         |
| Instance becomes stopped                  | ❌      | ✅          | ✅         | ❌         |
| Can start again                           | ✅      | ✅          | ✅         | ❌         |
| Useful for saving compute cost while idle | ❌      | ✅          | ✅         | —         |
| Fast resume of application state          | ❌      | ❌          | ✅         | ❌         |
| Permanent removal                         | ❌      | ❌          | ❌         | ✅         |

### Exam decision rule

```text
Need to restart the OS?
→ Reboot

Need to shut down temporarily and save compute cost?
→ Stop

Need to shut down but preserve RAM / resume quickly?
→ Hibernate

Need to permanently remove the instance?
→ Terminate
```

## EC2 billing by instance state

For normal EC2 instance usage:

| State           | Instance usage billed? |
| --------------- | ---------------------: |
| `pending`       |                      ❌ |
| `running`       |                      ✅ |
| `stopping`      |                      ❌ |
| `stopped`       |                      ❌ |
| `shutting-down` |                      ❌ |
| `terminated`    |                      ❌ |

### Important exception: Hibernation

When an instance is **hibernating**, instance usage is billed while it is in the `stopping` state.

```text
Normal Stop:
running → stopping → stopped
             ❌          ❌

Hibernate:
running → stopping → stopped
             ✅          ❌
```

So:

> **Normal stop → `stopping` = not billed**

> **Hibernate → `stopping` = billed**

Once the hibernated instance reaches `stopped`, EC2 instance usage charges stop. EBS storage charges still apply.

### Reserved Instance trap

A **Reserved Instance (RI) is a billing commitment**, not a special EC2 instance that you can start, stop, or terminate.

If an EC2 instance covered by an RI is stopped:

```text
EC2 instance
    ↓
STOPPED
    ↓
EC2 instance usage charge stops

Reserved Instance
    ↓
RI commitment continues
```

So:

> **Stopping the EC2 instance does NOT stop the Reserved Instance commitment.**

Likewise, terminating the EC2 instance does not cancel the RI.

```text
EC2 instance terminated
        ↓
EC2 instance usage charge → stops

Reserved Instance
        ↓
RI commitment → continues
```

AWS explicitly states that Reserved Instances applied to terminated instances continue to be billed until the end of their term according to the payment option.

### Decommissioned application + unused RI

Suppose:

```text
Web application
      ↓
Decommissioned
      ↓
EC2 instance no longer needed
      ↓
Reserved Instance still has 8 months remaining
```

The cost-effective actions are different for the **EC2 instance** and the **RI**:

1. **Terminate the unused EC2 instance**

   * stops EC2 instance usage charges
   * do not keep an unnecessary instance running

2. **Sell the unused Standard RI in the Reserved Instance Marketplace**

   * removes the unused RI commitment after the sale
   * the marketplace allows eligible customers to resell unused **Standard EC2 Reserved Instances**

### Important RI Marketplace rule

Only **eligible Standard Reserved Instances** can be sold in the Reserved Instance Marketplace.

```text
Standard RI
→ Can be sold

Convertible RI
→ Cannot be sold
```

Other important eligibility conditions apply, so not every Standard RI can necessarily be listed.

### SAA exam trap

Question:

> "A company decommissioned an application but still has Reserved Instances. What should it do to reduce costs?"

Think:

```text
Unused EC2 instance
→ Terminate the EC2 instance

Unused eligible Standard RI
→ Sell it in the Reserved Instance Marketplace
```

### What does NOT work?

> **"Stop the Reserved Instance."**

❌ There is no "stop RI" lifecycle operation. You can stop the **EC2 instance**, but the RI commitment continues.

> **"Terminate the Reserved Instance."**

❌ You terminate an **EC2 instance**, not the RI commitment.

> **"Cancel the RI."**

❌ An active RI generally remains a billing commitment for its term. For eligible Standard RIs, selling it through the Reserved Instance Marketplace is the relevant way to transfer the remaining commitment.

### Important distinction

```text
EC2 instance
= actual compute resource

Reserved Instance
= pricing commitment applied to eligible usage
```

### SAA memory rule

```text
Stop EC2
→ stops EC2 usage charges
→ does NOT stop RI charges

Terminate EC2
→ stops EC2 usage charges
→ does NOT cancel RI commitment

Sell eligible Standard RI
→ transfers the RI
→ removes your RI commitment after sale
```

## Instance families

An instance type such as `m7g.2xlarge` contains several pieces of information:

```text
m7g.2xlarge
││ │  │
││ │  └── size
││ └───── architecture / processor family
│└─────── generation
└──────── instance family
```

### Main families

| Family  | Purpose                                   | Common exam keywords                                                  |
| ------- | ----------------------------------------- | --------------------------------------------------------------------- |
| **M**   | General purpose, balanced CPU and memory  | web/app servers, general workloads                                    |
| **T**   | Burstable general purpose                 | occasional CPU spikes, dev/test, CPU credits                          |
| **C**   | Compute optimized                         | CPU-intensive workloads, batch processing, high-performance computing |
| **R**   | Memory optimized                          | in-memory databases, caches, real-time analytics                      |
| **X**   | Very high memory                          | SAP HANA, very large in-memory databases                              |
| **I**   | Storage optimized                         | high IOPS, low-latency local NVMe, NoSQL workloads                    |
| **D**   | Storage optimized with dense HDD capacity | distributed file systems, data warehousing, large sequential datasets |
| **P**   | GPU optimized                             | ML training, deep learning                                            |
| **G**   | GPU optimized                             | graphics, video rendering, ML inference                               |
| **Inf** | AWS Inferentia-based ML instances         | cost-efficient ML inference                                           |
| **Trn** | AWS Trainium-based ML instances           | ML training                                                           |

### Graviton

A `g` suffix such as:

```text
m7g
c7g
r7g
```

indicates an AWS Graviton processor based on **ARM architecture**.

Typical exam clues:

* best price-performance
* reduce compute cost
* sustainability
* Linux/application is compatible with ARM

Do not choose Graviton merely because the question says "newer generation." The workload must be compatible with ARM.

# Purchasing options

The important questions are:

* How long will the workload run?
* Is usage predictable?
* Can the workload be interrupted?

| Option                 | Commitment            | Typical use                                             |
| ---------------------- | --------------------- | ------------------------------------------------------- |
| **On-Demand**          | None                  | Short-term or unpredictable workloads                   |
| **Reserved Instances** | 1 or 3 years          | Predictable, steady EC2 usage                           |
| **Convertible RI**     | 1 or 3 years          | Predictable usage but instance configuration may change |
| **Savings Plans**      | 1 or 3 years          | Predictable spending with more flexibility              |
| **Spot**               | None                  | Interruptible, fault-tolerant workloads                 |
| **Dedicated Host**     | Host-level allocation | Hardware visibility and certain BYOL requirements       |
| **Dedicated Instance** | Dedicated hardware    | Hardware isolation without host-level control           |

## On-Demand

Use when:

* workload duration is uncertain
* usage is short-term
* no long-term commitment is desired
* interruption is not acceptable

Do not assume that every workload lasting less than one year must be On-Demand. The real question is whether a long-term commitment makes economic and operational sense.

---

## Reserved Instances

Best for predictable, steady EC2 usage.

Typical example:

```text
Application server
24 hours/day
365 days/year
Predictable capacity
```

### Standard RI

Provides a larger discount but less flexibility.

A Standard RI can be **sold in the Reserved Instance Marketplace** if it meets the marketplace eligibility requirements.

### Convertible RI

Allows more flexibility to change the instance configuration in exchange for a smaller discount.

Convertible RIs can be **exchanged** for another Convertible RI with different attributes during the term, but they **cannot be sold in the Reserved Instance Marketplace**.

Exam clue:

> "The workload is steady, but the instance family or configuration may change."

Think:

**Convertible RI.**

### Standard vs Convertible

| Feature                                     | Standard RI                                      | Convertible RI                                    |
| ------------------------------------------- | ------------------------------------------------ | ------------------------------------------------- |
| Higher potential discount                   | ✅                                                | ❌                                                 |
| Can modify certain attributes               | ✅                                                | ✅                                                 |
| Can exchange for different RI configuration | ❌                                                | ✅                                                 |
| Can sell in RI Marketplace                  | ✅                                                | ❌                                                 |
| Best when                                   | Usage is predictable and configuration is stable | Usage is predictable but configuration may change |

---

## Savings Plans

Savings Plans are based on a **committed spend per hour**, rather than a specific instance reservation.

### Compute Savings Plan

Most flexible.

Can apply across:

* EC2 instance families
* EC2 regions
* Fargate
* Lambda

Exam clue:

> "The company wants long-term savings but maximum flexibility to change instance families, regions, or use Fargate/Lambda."

Think:

**Compute Savings Plan.**

### EC2 Instance Savings Plan

Less flexible but usually offers a larger discount.

Commitment is tied to:

* a specific instance family
* a specific AWS Region

Example:

```text
m7i family
us-east-1
```

---

## Capacity reservation vs discount

A common exam trap is confusing **discounts** with **guaranteed capacity**.

A pricing commitment does not automatically mean AWS reserves EC2 capacity for you.

If the requirement is:

> "The company must guarantee that EC2 capacity will be available in a specific Availability Zone."

Think:

* **On-Demand Capacity Reservation**
* or a **Zonal Reserved Instance**, where applicable

A **regional RI** is primarily a billing discount and does not guarantee capacity in a particular AZ.

Savings Plans are also **billing commitments**, not capacity reservations.

---

## Spot Instances

Spot Instances use spare AWS capacity and can be reclaimed by AWS.

They are appropriate for workloads that can tolerate interruption.

Typical examples:

* batch processing
* image/video processing
* CI/CD workers
* distributed data processing
* stateless workers
* checkpointable workloads
* flexible background jobs

AWS provides a **two-minute interruption notice** for Spot interruptions.

### Spot is a poor choice when:

* the workload cannot tolerate interruption
* the application is not fault tolerant
* losing the instance would cause unacceptable data loss

Typical exam clue:

> "The workload can be interrupted and restarted, and minimizing cost is the priority."

Think:

**Spot.**

---

## Common cost pattern

If a workload has:

* predictable baseline usage
* unpredictable additional demand

a common architecture is:

```text
Predictable baseline
        ↓
RI / Savings Plan

Additional flexible capacity
        ↓
Spot / On-Demand
```

For example:

```text
100 instances normally required
        ↓
80 covered by Savings Plan
20 added using Spot when possible
```

The exact combination depends on interruption tolerance.

# Dedicated Host vs Dedicated Instance

Both provide physical hardware isolation from other AWS customers.

### Dedicated Host

You get visibility and control over the physical host.

Relevant when requirements involve:

* BYOL
* per-socket licensing
* per-core licensing
* host-level visibility
* physical host placement requirements

Exam clue:

> "Existing software is licensed per socket or per physical core."

Think:

**Dedicated Host.**

### Dedicated Instance

Provides hardware isolation, but you do not get the same host-level visibility and control.

Exam clue:

> "The company only requires hardware isolation for compliance."

Think:

**Dedicated Instance.**

# Placement groups

Placement groups control how EC2 instances are placed on underlying AWS infrastructure.

There are three main strategies:

| Placement group | How instances are placed                                                                                     | Main goal                                 | Typical workload                   | Easy memory           |
| --------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------- | ---------------------------------- | --------------------- |
| **Cluster**     | Instances are placed **close together** in the same AZ                                                       | **Low latency + high network throughput** | HPC, tightly coupled workloads     | **Together**          |
| **Spread**      | **Each instance** is placed on separate underlying hardware                                                  | **Individual failure isolation**          | Small number of critical instances | **Individuals apart** |
| **Partition**   | Instances are divided into **groups (partitions)**, and each group is placed on separate underlying hardware | **Group-level failure isolation**         | Kafka, Cassandra, Hadoop, HDFS     | **Groups apart**      |

## Cluster placement group

Instances are placed closely together within a single Availability Zone.

Provides:

* very low network latency
* high network throughput

Best for:

* tightly coupled HPC workloads
* applications requiring very fast instance-to-instance communication

Trade-off:

* concentrated failure domain

Exam clue:

> "Lowest network latency between EC2 instances."

Think:

**Cluster placement group.**

---

## Spread placement group

Instances are placed on distinct underlying hardware to reduce the chance of correlated hardware failure.

Best for:

* a small number of critical instances
* workloads where each instance should have an isolated failure domain

A spread placement group supports a limited number of instances per AZ.

Exam clue:

> "A few critical instances must not share the same underlying hardware."

Think:

**Spread placement group.**

---

## Partition placement group

Instances are divided into logical partitions.

Each partition uses separate underlying hardware, reducing the impact of a hardware failure.

Best for large distributed systems such as:

* Hadoop
* Cassandra
* Kafka
* HDFS

A partition placement group supports large numbers of instances and provides partition information through EC2 instance metadata, which allows topology-aware applications to distribute replicas intelligently.

Exam clue:

> "Large distributed system where instances should be separated into independent hardware groups."

Think:

**Partition placement group.**

### Easy memory rule

```text
Cluster   = close together
Spread    = isolate individual instances
Partition = isolate groups of instances
```

# Elastic Network Interface (ENI)

An **Elastic Network Interface (ENI)** is a virtual network interface attached to an EC2 instance.

A **VPC Interface Endpoint** is an AWS PrivateLink endpoint that creates ENIs inside your subnet.

An ENI can have properties such as:

* private IPv4 address
* secondary private IPv4 addresses
* IPv6 addresses
* MAC address
* security groups

The most important SAA concept is that a **secondary ENI can be moved between EC2 instances**.

This allows the network identity associated with that ENI to survive the failure of an EC2 instance.

---

## Primary ENI vs Secondary ENI

Every EC2 instance has a **primary network interface**.

It is created automatically when the instance is launched.

```text
EC2 Instance A
│
└── Primary ENI
    └── Primary private IPv4 address
```

A primary ENI is associated with that instance and is **not used as the portable failover interface** in the typical ENI failover pattern.

You can also create additional ENIs and attach them to an instance.

```text
EC2 Instance A
│
├── Primary ENI
│   └── Primary private IP
│
└── Secondary ENI
    └── 10.0.1.50
```

The secondary ENI is the important one for failover because it can be **detached and attached to another compatible EC2 instance**.

---

## ENI failover pattern

Suppose a dashboard is reachable through:

```text
dashboard.internal.example.com
        ↓
    10.0.1.50
```

The DNS record points to the private IP associated with a **secondary ENI**.

Initially:

```text
                    EC2 Instance A
                         │
                         │ attached
                         ▼
              ┌────────────────────┐
              │ Secondary ENI      │
              │ Private IP         │
              │ 10.0.1.50         │
              └────────────────────┘
```

Traffic flows:

```text
Client
  │
  │ dashboard.internal.example.com
  ▼
10.0.1.50
  │
  ▼
Secondary ENI
  │
  ▼
EC2 Instance A
```

If Instance A fails:

```text
EC2 Instance A
      ❌
```

The secondary ENI can be detached and attached to Instance B:

```text
                    EC2 Instance B
                         │
                         │ attached
                         ▼
              ┌────────────────────┐
              │ Secondary ENI      │
              │ Private IP         │
              │ 10.0.1.50         │
              └────────────────────┘
```

Now:

```text
Client
  │
  │ dashboard.internal.example.com
  ▼
10.0.1.50
  │
  ▼
Secondary ENI
  │
  ▼
EC2 Instance B
```

The client does not need to change the IP address.

### What actually moved?

**The ENI moved.**

The following network identity associated with that ENI remains available:

```text
Secondary ENI
├── private IP
├── MAC address
├── security groups
└── other ENI configuration
```

The EC2 instance itself was replaced.

---

## Important ENI limitation: Availability Zone

An ENI belongs to a subnet.

A subnet belongs to one Availability Zone.

Therefore:

> **An ENI can only be attached to an instance in the same Availability Zone.**

Example:

```text
AZ-A
├── Subnet A
│   └── Secondary ENI
│
└── EC2 Instance A
```

The ENI can be moved to another EC2 instance in **AZ-A**:

```text
AZ-A
├── Secondary ENI
└── EC2 Instance B
```

But it cannot simply be moved to an instance in AZ-B.

For **cross-AZ failover**, use mechanisms such as:

* Route 53
* Elastic Load Balancing
* application-level failover
* other multi-AZ architecture patterns

### Exam clue

> "Primary EC2 instance fails and the replacement instance must immediately use the same private IP."

Think:

**Secondary ENI → detach → attach to replacement instance**

---

## Multiple ENIs

You can attach multiple ENIs to an EC2 instance when a workload needs multiple network interfaces.

This can be useful for:

* separate network paths
* management networks
* traffic inspection appliances
* network appliances
* multi-homed instances

Example:

```text
EC2 Instance
│
├── ENI 1
│   └── Application network
│
└── ENI 2
    └── Management network
```

This is called a **multi-homed** configuration.

# Elastic IP address

An **Elastic IP (EIP)** is a static public IPv4 address that can be associated with an AWS resource such as an EC2 instance.

The default public IPv4 address assigned to an EC2 instance is not persistent across a **stop/start** operation.

Therefore:

> "The application must keep the same public IPv4 address after an EC2 stop/start."

Think:

**Elastic IP.**

An EIP can be remapped to another EC2 instance, including an instance in another Availability Zone.

### EIP vs ENI

| Feature          | ENI                               | Elastic IP           |
| ---------------- | --------------------------------- | -------------------- |
| Network identity | Private/network interface         | Public IPv4          |
| Typical use      | Private IP failover               | Stable public IPv4   |
| Movable          | Secondary ENI can move            | Can be remapped      |
| Cross-AZ         | No, ENI is AZ-specific            | Yes                  |
| Main exam use    | Preserve private network identity | Preserve public IPv4 |

### Best practice

Avoid using EIPs when an AWS-managed DNS/load-balancing solution is more appropriate.

Common alternatives:

* Application Load Balancer
* Network Load Balancer
* Route 53
* AWS Global Accelerator

# User data

EC2 user data is commonly used to run initialization commands when an instance launches.

Typical uses:

* install packages
* configure applications
* download configuration
* start services
* bootstrap an instance

Example:

```bash
#!/bin/bash
dnf install -y nginx
systemctl enable --now nginx
```

Exam clue:

> "Automatically install and configure software when the instance launches."

Think:

**User data.**

Do not confuse user data with instance metadata.

# Instance metadata

EC2 Instance Metadata provides information about the running instance from inside the instance.

The metadata service is available through:

```text
http://169.254.169.254/
```

Examples of information available through metadata include:

* instance ID
* Availability Zone
* local IP information
* IAM role credentials
* placement information

### IMDSv2

IMDSv2 adds session-oriented protection to the metadata service.

It requires a token before metadata can be requested.

Exam clue:

> "Protect the EC2 metadata service against SSRF-style attacks."

Think:

**Require IMDSv2.**

# Question patterns

> **"Nightly batch job processes images. The jobs can be restarted if interrupted. Minimize cost."**

→ **Spot Instances**

---

> **"Critical workload cannot tolerate interruption."**

→ **Do not use Spot.** Consider On-Demand, Reserved Instances, or Savings Plans depending on usage.

---

> **"SAP HANA requires a very large amount of memory."**

→ **X family**

---

> **"In-memory cache or memory-intensive analytics."**

→ **R family**

---

> **"Train a deep learning model."**

→ **P family**

---

> **"Serve ML predictions using specialized inference hardware."**

→ **Inf family**

---

> **"Existing software is licensed per physical socket or core."**

→ **Dedicated Host**

---

> **"Guarantee EC2 capacity in a specific Availability Zone."**

→ **On-Demand Capacity Reservation or appropriate zonal capacity reservation mechanism**

---

> **"T3 performs well for a while and then slows during continuous CPU usage."**

→ **CPU credits exhausted**

---

> **"A T3 workload needs to keep bursting even after credits are exhausted."**

→ **T Unlimited**, with possible additional charges

---

> **"The public IP changed after the instance was stopped and started."**

→ **Elastic IP**

---

→ **Move a secondary ENI to the standby instance**

---

> **"The same private IP must move across Availability Zones."**

→ **A secondary ENI cannot solve this because ENIs are AZ-specific. Use DNS, load balancing, or another multi-AZ architecture.**

---

> **"A small number of critical instances must be isolated from hardware failures."**

→ **Spread placement group**

## Lifecycle decision rule

```text
Need to restart the OS?
→ Reboot

Need to shut down temporarily and save EC2 compute cost?
→ Stop

Need to shut down but preserve RAM and resume faster?
→ Hibernate

Need to permanently remove the instance?
→ Terminate
```
